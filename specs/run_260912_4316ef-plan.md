# Automatic Smith pipeline healing

## Goal and scope

When an executing pipeline would otherwise terminate unsuccessfully, ask Smith for a validated repair to the pipeline's remaining phases and continue the **same run, in the same worktree, from the failure point**. Allow at most **two Smith proposal calls per run ID**, including unsuccessful calls. A failure after two applied repairs must terminate without a third call. Runs that would be accepted must not call Smith.

This applies to both generated/Orchestrator runs and manually selected pipelines. It changes the run-owned pipeline snapshot, not the stored pipeline definition or shared agent roster.

### Decisions the implementation must preserve

1. **This is pipeline healing, not command healing.** Keep `engine/healing.ts`, flake reruns, envelope/gate corrections, and `feedbackTo` recovery working as they do today. Smith is the final recovery layer, reached only after those paths return a terminal failure. Their existing budgets do not replenish or consume the two Smith calls. `phase.heal: false` disables command healing, not pipeline amendment.
2. **Count calls, not successful amendments.** One invocation of the proposal adapter opens at most one one-shot and sends at most one prompt. Invalid schema, invalid domain proposals, thrown model calls, and calls interrupted by cancellation consume a reserved call. Remove the current nested schema-correction loop, which can open more than two Smith sessions despite a two-amendment budget.
3. **Cancellation and operator interruption are not failures to heal.** Run cancellation aborts the in-flight Smith turn, prevents application of its late answer, starts no further phases or proposals, and settles `killed`. An operator phase interruption still settles `rejected` without Smith or acceptance evaluation; simultaneous cancellation wins.
4. **Acceptance remains engine-owned.** Preserve the existing distinction between ordinary `rejected` outcomes and infrastructure/runtime `failed` outcomes. The request's “fail the pipeline” means terminal non-success; do not rename every phase rejection to `failed`. Preserve the existing hard rejection for a PR/issue phase that failed to create its artifact, even if an earlier acceptance flag is green.
5. **An empty proposal is a no-op.** `null`/no structured submission, or a schema-valid submission with `phases: []`, means no repair. Record that the call returned no replacement, leave phases, acceptance, plan, agents, and amendment count unchanged, and settle with the original unsuccessful verdict. Do not spend another call immediately on an explicit no-op. A malformed nonempty proposal or a model exception may be retried once using the remaining global budget, with validation/error feedback.
6. **Repairable failure points are inside the phase pipeline.** Cover phase aborts, phase-runner exceptions, and a negative final acceptance verdict with an identifiable phase. Worktree creation/submodule initialization/setup failures before phase 1, registry crash/orphan sweeps, and post-run merge/landing errors keep their existing fail-closed behavior: there is no valid phase execution point to repair by amending a tail. Do not call Smith from `finish()`, `RunRegistry.settleRun()`, or the registry's catch-all.
7. **No UI or approval detour.** Use a dedicated, read-only Smith repair one-shot. Do not send to the operator's interactive `SmithChatSession`, enqueue a `SmithService` approval proposal, invoke `startRun`, or call the public Continue action automatically. The engine validates and applies this narrowly scoped repair directly.

## Current implementation and gaps

Relevant code already provides much of the mechanism:

- `apps/desktop/src/main/engine/executor.ts`: `runFrom`, `tryReplan`, `checkAmendment`, `applyAmendment`, `replanEvidence`, and resume-time attempt restoration.
- `apps/desktop/src/main/orchestrator/replan.ts`: read-only, schema-bound tail proposal adapter and its prompt. It currently identifies as the Orchestrator, requires `GeneratedRunPlan`, and retries inside `envelopeRetries`.
- `apps/desktop/src/main/engine/registry.ts`: injects that adapter only when `input.plan` exists, using the planning model.
- `apps/desktop/src/main/trace/tracer.ts`: `amendRun` atomically replaces queued rows and snapshots; `replanAttempts` derives usage from proposal/amendment events.
- `apps/desktop/src/main/engine/acceptance.ts`: the pure acceptance function. A later aborted phase does not necessarily make a `phase_flag` pipeline unsuccessful.
- `apps/desktop/src/main/engine/phase-history.ts`: selects the latest row for each active phase name, excluding superseded amendment history.
- `apps/desktop/tests/main/engine/replanning.test.ts`: real-Git coverage of generated-run amendments, invalid proposals, and cancellation. Its manual-run exclusion and nested retry expectations must change.

Specific gaps:

- Smith is not currently the proposal agent, and manual runs are explicitly excluded twice.
- `runFrom` asks for a replan on every non-interrupted phase abort before checking whether the run would actually be accepted. Conversely, a rejection discovered only by final acceptance never asks for one.
- The two outer attempts can each invoke several model sessions through the inner schema retry loop.
- A started call is not durably counted until it answers or throws. Killing/crashing during the call can restore unused budget on Continue.
- The trace amendment API requires a generated plan, and manual runs have no persistence path for synthesized repair agents.
- Tail replacement assumes every row after the failed phase is still queued. Feedback re-entry can leave failed or successful historical rows there; these must be retained rather than deleted or treated as an amendment crash.

## Implementation plan

### 1. Make the proposal adapter a bounded Smith turn

In `orchestrator/replan.ts`:

- Keep the small `Replanner` interface (`propose` and optional `abort`) and `PipelineAmendment | null` return type.
- Replace `ReplanProposalInput.plan` with explicit run facts:
  - `request: string` — the executor's full active request, not the truncated `RunRow.request`;
  - `pipeline: PipelineDef` — the active definition, including its acceptance criterion;
  - `allowedModels: Array<{ model: string; reasoningEffort: ReasoningEffort }>` — explicit run appointments the engine permits in replacement phases;
  - keep `roster`, `commands`, `failedPhase`, `completed`, `remaining`, `evidence`, and `attempt`;
  - add optional `previousIssues: string[]` for a rejected first call's validation/model error feedback.
- Change all generated-plan-specific prompt and color-offset accesses to those independent inputs. Hydrate new agents using the active roster length as the color offset.
- Add `resolvePipelineHealingModel(settings: AppSettings)` returning `{ model, reasoningEffort }`:
  - a concrete `smithModel` uses `smithReasoningEffort`;
  - missing/`inherit` `smithModel` uses `defaultModel` (or `inherit` if there is no concrete default), with `defaultReasoningEffort` for a concrete default;
  - if both inherit, retain `smithReasoningEffort` and let the existing enabled-model runtime resolution operate;
  - never use `plan.model` or `healingModel` to choose Smith's proposal model. Replacement-phase appointments are a different concern.
- The standing prompt must begin by identifying the agent as **Smith, repairing this Foundry pipeline**. Describe the automatic, run-scoped authority: propose the smallest useful replacement starting at the failed phase; preserve the completed prefix, run goal, acceptance criterion, isolation, and verification intent; reuse roster agents where possible; new agents are run-local; no feedback into the completed prefix; no claim that the repair succeeded.
- Include shared composition-rule bullets and keep the explicit untrusted-task-data instruction. The prompt must include the failure detail, failed phase definition, remaining phase definitions, acceptance, completed names and available envelope summaries, configured commands, allowed model/effort appointments, and any first-call rejection issues. Use full phase definitions for the failed/remaining phases so Smith can retain gates, inputs, and feedback links when editing, but do not dump full roster system/user prompts. Keep bounded failure evidence and existing roster summaries.
- Explain `{"reason":"...","phases":[],"agents":[]}` as the opt-out answer when there is no defensible repair. Do not turn an empty array into removal of the failed tail.
- Use `z.array(pipelineSchema.shape.phases.element)` for amendment phases instead of inheriting the pipeline array's `min(1)`. Do **not** relax the ordinary pipeline schema. Retain strict top-level amendment parsing and synthesized-agent validation.
- Remove the loop over `1 + FIXED_ENGINE_DEFAULTS.envelopeRetries` and its repeated one-shot creation. Each `propose` call opens one read-only session, sends once with `submit_result` output format, parses once, and aborts/disposes in `finally`.
- Return `null` for no structured submission or an interrupted/aborted turn. Return a parsed empty amendment for `phases: []` (the executor handles it before all mutation). For malformed nonempty structured output, throw an error containing the parser's field-level issues; the executor owns whether a second call is allowed. No hidden correction send/session is permitted in this adapter.
- Preserve late-bound `cwd()` and `abort()` behavior. An adapter aborted before a call must not open a session. Do not add write-capable or Smith application tools to the one-shot.

### 2. Decide whether the run needs healing before asking Smith

Refactor `Executor.runFrom` into a small outer recovery loop plus a private phase-walk helper, rather than adding more nested branches to the current loop. Keep sessions open until a final verdict so repair phases can reuse their existing bounded session machinery.

The phase-walk helper should return a discriminated stop result: completed, cancelled, interrupted, or stopped at a failure (index, detail, and whether the existing outcome is forcibly non-success). It retains checkpointing, between-phase compaction, `next`/`goto`, and the bounded step guard.

Outer-loop behavior:

1. Walk from the requested index using the existing runners and local recovery paths. Do not invoke Smith on a `goto` that is still using its feedback budget.
2. Check cancellation first; then honor operator interruption without evaluating acceptance or healing.
3. Derive the current verdict using `decideAcceptance` and **active** phase rows, envelopes, and command results.
4. For a phase abort, ask Smith only if this verdict is negative, **or** the failed phase's effective envelope is `pr`/`issue` and therefore the existing artifact-failure exception requires rejection. A green earlier acceptance flag plus an unrelated later abort must still finish accepted without a Smith call.
5. A final negative acceptance verdict after a normal walk also needs recovery:
   - for `phase_flag` or `envelope_status`, use the named acceptance phase as the failure point;
   - for `all_phases_pass`, use the first active non-success/non-skipped row;
   - for `last_phase_pass`, use the final active phase;
   - if there is no valid phase anchor, settle without inventing a phase or calling Smith.
   Include the negative acceptance reason and the phase's envelope in evidence even when that phase row itself was successful (for example, a manual approval phase without a disapproval gate).
6. Catch exceptions specifically around phase-runner execution, after a phase is known. Close its active row as failed, trace the original exception, and expose that failure point as a forcibly unsuccessful stop to the same recovery decision (the existing registry exception path would fail even with an earlier green flag). If no repair applies, preserve the prior runtime-exception `failed` status. Do not swallow tracer/database errors or broadly catch setup/landing failures as repair proposals.
7. A loop-guard failure may use an already failed active row as its anchor. Do not mark a successful prefix phase failed merely to create a repair target. A missing feedback target or any guard stop with no usable anchor remains a terminal stop with existing semantics.
8. If a valid amendment applies, set the next walk index to the failure index and continue, without settling/reopening the run or running setup again. No recursion into `run()`, `resume()`, or the registry.
9. Otherwise close sessions once and finish with the original verdict/status and failure detail. Do not take a second path through final acceptance that asks Smith again for the same empty/exhausted proposal. Preserve useful original failure text; an added “Smith healing exhausted (2/2)” explanation must not replace it.

Keep the phase-walk guard bounded across this outer loop. It is acceptable to give each successfully amended walk the existing finite `phases.length + 32` walk budget, because there can be at most two amendments. Invalid/no-op proposals must not restart the walk or increase its step budget.

### 3. Reserve and restore the two-call budget

In `Executor.tryReplan`:

- Remove `!this.plan` from eligibility. Missing injected support still means no automatic healing (useful for no-runtime test harnesses).
- Reject entry when cancelled or `replanAttempts >= FIXED_ENGINE_DEFAULTS.replanAttempts`.
- Before each actual proposal invocation, increment the executor count and synchronously record a Tracer event named **`replan proposal started`**, type `log`, with `{ actor: 'smith', attempt, budget: 2, phase: failedPhase.name }` under the failed phase ID. If reserving the call cannot be persisted, do not call the model.
- Register its abort through `onCancel`, re-check cancellation before invocation, and unregister in `finally`. Check cancellation immediately after awaiting the answer and before validating/applying it. A late valid result must not revive a killed run.
- A `null` or empty-phases result records a no-op via the existing rejected-proposal log path and returns false immediately; ignore any accompanying new agents and do not call `amendRun`.
- A parse/model exception or a nonempty amendment rejected by rails records the concrete failure and may try the remaining slot. Pass the issues to the next proposal. Two such attempts are the same two slots that would otherwise allow two applied repairs.
- An accepted nonempty amendment returns true immediately. Do not proactively spend slot two until the amended execution actually fails again.
- Keep the count on the Executor for the entire run and restore it from `tracer.replanAttempts(runId)` in `resume()`. Do not reset it after a phase succeeds, at a new phase, during feedback, or after amendment application.

In `Tracer.replanAttempts`, keep recognizing historical `type = 'replan'` and `name LIKE 'replan proposal%'` events; the new started event deliberately fits that query. Count the highest finite positive integer attempt, not the number of events (started/rejected/applied can describe one call). Ignore malformed attempt values and retain legacy attempt events for existing runs. A stored count at or above two blocks all future automatic Smith calls for that run.

### 4. Validate and apply a replacement without damaging the completed prefix

Keep the existing normal rails in `checkAmendment`:

- validate new agents and reject duplicate active names;
- validate the full candidate pipeline with the active/new agents, commands, and envelopes;
- run `preflightForRun`;
- require explicit allowed agent-phase model appointments with `phaseModelIssues`;
- apply `generatedCompositionIssues` to the automatically authored replacement tail for **both** run origins. Do not retroactively force a manual completed prefix through generated-tail composition rules;
- reject `feedbackTo` into the immutable prefix;
- keep the pipeline ID, goal, acceptance, and isolation unchanged. Ordinary validation must reject removal of a named acceptance target.

Replace the plan-only `confirmedModelIds` dependency with explicit allowed appointments:

- Generated runs: derive concrete model/effort choices from the active confirmed plan, as today. Never authorize Smith's proposal model as a replacement-phase model merely because it authored the repair.
- Manual runs: derive concrete effective appointments from active pipeline phases using the same precedence as `appointedModel`/`resolveAgentExecution` (phase override, agent, run default). Include the concrete run default so a code-only manual pipeline can add a repair agent. Exclude `inherit` and deduplicate model/effort pairs.
- Send these same choices to the prompt and use their model IDs for the rail. A run with no concrete authorized agent appointment can still accept a valid code-only amendment; do not invent a model ID or silently drop the model rail.

Application details:

- Candidate phases are `oldPhases.slice(0, failedIndex)` plus the replacement tail. The failed definition is replaced, not marked successful. The first replacement executes at `failedIndex`.
- Preserve prefix definitions, phase IDs, envelopes, outputs, sessions, and worktree edits. Do not restore the whole tree to the run's starting commit or rerun completed phases/setup.
- For the old tail, pass **only rows currently `queued`** in the deletion list to `Tracer.amendRun`. Retain all terminal rows, including prior successful/failed feedback attempts and the failed row itself, as history. A genuinely running row cannot be superseded; reject/fail closed rather than deleting in-flight work.
- Queue fresh row IDs for every replacement definition. Clear old-tail entries in the executor's phase-ID, envelope, command-result, feedback, and recovery-note maps; install the new row IDs. Retain existing bounded runner-local counters rather than replenishing local healing just by reusing a name. Append only accepted new agents to the shared executor roster array used by the agent runner.
- If `this.plan` exists, update its pipeline, synthesized agents, and deduplicated warnings. Otherwise retain `plan: null`; never fabricate `GeneratedRunPlan` or flip `orchestrated` to true for a healed manual run.
- Keep existing `replan`/`pipeline amended` trace payload fields (`attempt`, `reason`, `evidence`, `before`, `after`) compatible. Add `actor: 'smith'` and the newly accepted `agents` definitions. Preserve the current `before` convention (the previous tail after the failed phase) so the existing event UI and e2e seed remain compatible.

### 5. Persist manual amendments and support Continue without resetting healing

In `Tracer`:

- Make `amendRun.input.plan` nullable and add optional `agents: AgentDef[]` defaulting to `[]`, for compatibility with current e2e seeds/callers.
- Persist SQL `NULL` for a manual plan, not the string `"null"`; write `plan.json` only for a non-null plan. Always maintain the pipeline snapshot and `pipeline.json` mirror.
- Keep the snapshot update, amendment-count increment, deletion of queued rows, creation of fresh rows, and accepted `replan` event (including new-agent definitions) inside the existing single SQLite transaction. The engine must not update its in-memory pipeline/roster until this operation returns successfully.
- Add `amendmentAgents(runId): AgentDef[]`: query accepted `replan` events directly in creation order, not a paginated UI event page; parse each optional `agents` array with the existing `agentSchema`; treat legacy absent arrays as empty; return valid accepted definitions deduplicated by name. Rejected/started events must never introduce agents. This is run-owned data, not a roster-store write.
- Add `runPipeline(runId): PipelineDef | null`, reading/parsing `pipeline_snapshot_json` defensively like `runPlan`. This is the authoritative snapshot after a committed amendment; the JSON file remains a useful mirror, not the only recovery source.

In `RunRegistry`:

- `executorFor` injects `replanningSupport` whenever `oneShot` exists, for both run origins, using `resolvePipelineHealingModel(settings)` and the existing lazy worktree lookup. Keep command `healingSupport` independently wired.
- In `resume`, read `tracer.runPipeline(runId)` first, with the old `pipeline.json` path as compatibility fallback when no database snapshot is available, then apply the existing Continue eligibility checks.
- Merge the ordinary input roster and existing plan agents as before, then overlay `tracer.amendmentAgents(runId)` by name so already accepted run-owned repair agents survive restart and win over a later shared-roster collision. Do not save them to a project/global roster. Pass this merged roster and the nullable saved plan to the new Executor.
- The same run ID and `resume()`'s restored count enforce the cap across Continue/app restart. A new independent run receives its own two slots.

## Risks and safeguards

- **Duplicate recovery entry points can violate no-op and call limits.** Use one outer unsuccessful-termination decision; do not independently heal both an abort and the same final rejection.
- **Attempts and applications are different facts.** Reserve calls before awaiting and keep `runs.amendments` as applied repairs only. Tests must count actual factory calls/sends, not just amendments.
- **Acceptance can intentionally ignore some phase failures.** Reuse `decideAcceptance`; keep PR/issue and interruption exceptions explicit rather than globally forcing all red phase rows to reject.
- **Tail rows are not always queued.** Preserve terminal feedback/acceptance history and choose active rows by name/identity; never rewrite the successful prefix or historical failed rows to green.
- **Manual runs must not become fake generated runs.** Nullable plan persistence and accepted run-owned agents avoid changing UI origin, shared definitions, or requiring an Orchestrator confirmation to resume.
- **Smith repairs are untrusted proposals, not administrative commands.** Keep read-only tools, schema/normal rails, model restrictions, immutable acceptance/isolation, and bounded evidence. Do not reuse the chat's approval bypass or expose broad application mutation tools.
- **Crash durability matters more than a clean reply.** Started events must count after restart, and a committed pipeline snapshot must be readable independently of its file mirror. The cap fails closed if an attempted call did not leave a successful repair.
