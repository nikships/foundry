# Plan: Persistent dark/light themes for the Foundry desktop app

## Goal

Add a persisted `dark`/`light` application theme setting, expose it in Settings → App, apply it to the whole renderer immediately, and keep the Electron window background and browser color scheme synchronized. Preserve the existing semantic CSS-token API so screens and components do not branch on theme.

## 1. Add and persist the theme setting

### `apps/desktop/src/shared/types.ts`

- Define `export type AppTheme = 'dark' | 'light'` beside the settings types.
- Add `theme: AppTheme` to `AppSettings`, with a short comment that it controls the application-wide desktop palette and defaults to dark for existing installs.

### `apps/desktop/src/main/store/settings.ts`

- Import `AppTheme` as a type.
- Add `theme: z.enum(['dark', 'light'])` to `appSettingsSchema`.
- Add `theme: 'dark'` to `defaultSettings()` so existing users retain today’s appearance.
- Extend `migrate()` so a missing theme receives the default and any hand-edited value other than `dark` or `light` is repaired to `dark`. Keep the current unknown-key stripping behavior.
- Leave the existing `appearance` compatibility/unknown-key test behavior intact; the new supported key is `theme`, not `appearance`.
- Keep writes atomic through `JsonStore`; no separate theme file or renderer local-storage preference is allowed.

### `apps/desktop/src/main/context.ts` and `apps/desktop/src/main/ipc/settings.ts`

- Add a main-process method on `AppContext` for applying the native window background, e.g. `attachWindow(window: BrowserWindow)` and `applyTheme(theme: AppTheme)`. Store the current `BrowserWindow` reference only in main; never expose Electron to the renderer.
- Use `#020202` for dark and `#f7f7f5` (or the exact light `--bg-base` value selected in the token sheet) for light. Keep the mapping in one main-process helper so initial and runtime colors cannot diverge.
- Update the settings IPC router context type to include the theme-application callback. After a successful `ctx.settings.patch`, apply `result.settings.theme` before broadcasting `settings-changed`; rejected patches must not change the native window.
- Keep the existing `FoundryApi.settings` contract: theme travels as the existing `Partial<AppSettings>` patch and requires no new IPC channel.

### `apps/desktop/src/main/main.ts`

- Make `createWindow` accept the initial `AppTheme` and set `BrowserWindow.backgroundColor` from the same dark/light mapping used by `AppContext`.
- After constructing `AppContext` and before opening the renderer, read `ctx.settings.get().theme`, create the window with that theme, and attach the created window to the context. This makes the first native paint match a persisted light setting.
- Preserve the existing `ready-to-show`, sandbox, preload, single-instance, bridge, updater, and companion ordering.

## 2. Apply the theme without flashes or restart

### `apps/desktop/src/renderer/index.html`

- Change the color-scheme meta declaration from dark-only to advertise both supported schemes (`dark light`).
- Change the FOUC guard to keep `#app` hidden until a theme has been loaded, for example `html:not([data-theme-ready]) #app { visibility: hidden; }`. Keep `html`/`body` transparent so the native window background is visible while the renderer is hidden.
- Do not add an inline script or network dependency; the existing CSP and preload-only startup model must remain unchanged.

### `apps/desktop/src/renderer/main.tsx`

- Keep setting `data-brand="factory"` before React renders.
- Set a dark `data-theme` and dark `style.colorScheme` only as the safe pre-settings fallback; do not treat it as the user’s persisted value.
- Do not mark `data-theme-ready` here. The ready marker must be set only after the settings store has supplied the actual theme.

### `apps/desktop/src/renderer/stores/app.tsx`

- Import `AppTheme` if a typed helper is useful.
- Add an effect driven by `settings?.theme` that updates all three root-document values together:
  - `document.documentElement.dataset.theme` (`dark` or `light`)
  - `document.documentElement.style.colorScheme`
  - `document.documentElement.dataset.themeReady = 'true'`
- Run this effect whenever `refreshAll` replaces settings, including a `settings-changed` push, so a successful Settings patch changes every screen immediately.
- Avoid a second renderer source of truth: the React settings state remains the source for controls, while the root attributes are the CSS integration point.

## 3. Add complete light-mode semantic tokens

### `apps/desktop/src/renderer/design/tokens-factory.css`

- Keep the existing dark Factory values as the default and/or `[data-theme='dark']` values.
- Add a `:root[data-brand='factory'][data-theme='light']` override block with every semantic color used by the app, not just the base surfaces. It must define:
  - surfaces: `--bg-void`, `--bg-base`, `--bg-panel`, `--bg-raised`, `--bg-hover`, `--bg-active`, `--bg-input`, `--bg-sidebar`, `--bg-titlebar`
  - lines: `--line-faint`, `--line`, `--line-strong`
  - text: `--text`, `--text-dim`, `--text-faint`, `--text-ghost`
  - accent: `--accent`, `--accent-bright`, `--accent-deep`, `--accent-dim`
  - categorical colors and their dim variants: purple, amber, green, red, blue
  - all `--status-*` aliases
  - shadows/overlays used by the renderer
- Use a warm near-white base and white panels, dark readable text, and a darker orange accent for light-background contrast. Use darker light-mode status hues where needed so status text/badges remain readable; dim variants must be translucent fills rather than opaque dark patches.
- Add semantic foreground/overlay tokens needed by shared controls, such as `--on-text` (dark label on dark-mode light buttons and light label on light-mode dark buttons), `--text-strong` (hover state for inverted controls), and `--overlay` (modal/sheet/palette scrims).
- Ensure the light block is complete rather than relying on partially inherited dark values; this prevents a forgotten dark status or line token from leaking into light mode.

### `apps/desktop/src/renderer/design/tokens-base.css`

- Replace hardcoded inverted-button colors (`#020202`/`#ffffff`) with the new semantic foreground tokens (`--on-text`/`--text-strong`). Keep the existing button geometry and behavior.
- Keep this file structural; all actual palette values belong in `tokens-factory.css`.

### Theme-sensitive component CSS/inline colors

Refactor the existing hardcoded dark/white colors identified in the renderer audit so light mode is coherent across overlays, controls, modals, tables, and status surfaces:

- `ModalShell.module.css`, `SideSheet.module.css`, and the Settings palette scrim in `SettingsScreen.module.css`: use `var(--overlay)` instead of fixed `rgba(2,2,2,...)`/black backdrops.
- `Dropdown.module.css`, `AgentIconPicker.module.css`, `SmithBubble.module.css`, `SmithEntityComparisonDesign.module.css`, `ContextBreakdown.module.css`, `DesignScopeControl.module.css`, and `PipelineCanvas.module.css`: route shadow/outline colors through the semantic shadow tokens where the existing fixed black shadows would be too heavy in light mode. Preserve layering and z-index behavior.
- `AgentIconPicker.tsx`: replace inline `rgba(255,255,255,0.09)` and `#0a0a0a` fallbacks with `var(--line)` and `var(--bg-panel)`/`var(--bg-raised)` so swatches follow the active palette while retaining their chosen hue.
- `PipelinesScreen.module.css`: replace the dry-run button’s fixed black/white foregrounds with `--on-text` and `--text-strong`.
- `RosterScreen.module.css`: replace the white-only hover mix with a mix based on `var(--text)`.
- `Sidebar.module.css`: replace any fixed black label used on a colored status badge with the appropriate semantic foreground token.
- Leave QR code foreground/background explicitly black and white in `QrCode.tsx`/the QR frame because QR contrast is intentional and independent of the application palette.
- Re-run the renderer color-literal search after edits. Remaining literals must be either data/avatar colors, QR colors, or deliberate image/mask colors; no modal scrim or general UI surface may remain hardcoded dark.

## 4. Add the Settings picker

### `apps/desktop/src/renderer/screens/SettingsScreen.tsx`

- Use `useApp()`’s existing `settings` and `patchSettings` path; do not add component-local persistence.
- In the App pane, add a new `Section` before Notifications:
  - label: `Appearance`
  - note: `Choose the palette Foundry uses across the desktop.`
- Render a labeled `Dropdown` (or the existing segmented control only if it supports the same accessible/testable behavior) with exactly two options: `Dark` (`dark`) and `Light` (`light`).
- Bind its value to `settings.theme`; on selection call the existing `set({ theme: nextTheme })` helper so validation errors use the existing Settings error banner and successful patches update AppContext immediately.
- Add a stable `data-testid="settings-theme"` to the picker trigger and an accessible label such as `Theme`.
- Show a short hint that the choice saves automatically and applies immediately. Do not add a Save button or relaunch requirement.

### `apps/desktop/src/renderer/view-models/settings-search.tsx`

- Add an `Appearance` entry to `SETTINGS_SECTIONS` under the App/general grouping with the exact label/note above and keywords including `theme`, `appearance`, `dark`, `light`, `palette`, and `color`.
- Keep the section label exactly synchronized with the new `Section` call so search jumps to `data-sec="appearance"`.
- If the existing App pane hint or registry prose mentions only notifications/updates/phone/maintenance, expand it to mention appearance/theme.

### `apps/desktop/src/renderer/mockFoundry.ts`

- Add `theme: 'dark'` to `defaultMockSettings()`.
- Keep the existing mock `settings.patch` merge and `settings-changed` listener behavior so web preview exercises the same immediate root-theme effect.

## 5. Tests and regression coverage

### `apps/desktop/tests/main/store/settings-store.test.ts`

Add a focused theme block covering:

1. fresh installs default to `dark`;
2. a settings file missing `theme` migrates to `dark` (both `migrate()` and `SettingsStore.get()`);
3. invalid stored values migrate back to `dark`;
4. `patch({ theme: 'light' })` succeeds, updates the store, and writes `light` to `settings.json`;
5. an invalid patch is rejected and leaves the last valid theme unchanged.

### `apps/desktop/tests/renderer/settings-search.test.ts`

- Assert the registry contains the new `appearance` jump target under the App pane.
- Assert a query such as `light theme` or `dark mode` returns the App/Appearance result.
- Update any registry expectations that enumerate the App sections, without weakening duplicate-target coverage.

### `apps/desktop/tests/e2e/settings.spec.ts` (new)

Use `seedOnboardedFixture()` and `launchFoundry()` with the isolated user-data directory:

1. wait for the onboarded Runs screen, open Settings, and select the App pane;
2. assert the Appearance section and Dark value are visible initially;
3. choose Light through `data-testid="settings-theme"`, then assert without relaunch that `document.documentElement.dataset.theme` is `light`, `style.colorScheme` is `light`, and a representative computed surface/background differs from the dark value;
4. choose Dark again and assert the root marker and computed colors switch back immediately;
5. choose Light, close the Electron app, relaunch using the same user-data directory, and assert the picker/root still report Light.

Keep this as an Electron UI regression test rather than a renderer unit test because the real DOM, CSS variables, native window initialization, and persisted settings all matter. Do not introduce a second browser harness.

The final `npm run check` is authoritative and must pass type checking, lint, formatting, knip, coverage, build, CSS collision checks, documentation checks, and dependency audit. During manual review, verify both themes on Settings, Runs, Design, Inspector, Smith, and modal/dropdown surfaces; confirm switching does not require navigation or restart and that a relaunch starts with the persisted theme.
