# Plan: FOU-349 — Persist orchestrator proposals and allow parallel run creation

## Goal

After submitting an orchestrated prompt the composer stays usable immediately.
Each orchestrator proposal is an independent durable record created **before**
any run exists. Multiple proposal-generation sessions run concurrently without
implicitly cancelling or replacing each other. Generating / ready / failed
proposals appear in the Activity sidebar before a run exists (project-scoped),
survive navigation, renderer reconnection, and app restart, and stream
progress independently of the originating composer/hook. Accepting a proposal
creates exactly one run; the accepted proposal becomes the persisted run plan
with the exact accepted snapshot retained. Cancellation vs discard for
still-generating proposals is defined.

No guessing for the builder: every file, signature, SQL, IPC name, ordering
rule, and test case is spelled out below.

## Non-goals (do not do)

- No change to plan composition rails, prompt wording, cast pool, golden
  shapes, replan budgets, healing, executor sequencing, boundary diffing.
- No change to `apps/website/`, `apps/android/`, `resources/`, builtin seeds.
- No network/model calls in tests. No new phase kind, gate, envelope,
  acceptance kind, or `FIXED_ENGINE_DEFAULTS` value.
- Do not rewrite `specs/orchestrated-runs.md` (historical).
- Do not invent per-build commit phases or change acceptance derivation.

## Design

### 1. Proposal record (durable, project-scoped, independent)

New shared type in `apps/desktop/src/shared/types.ts`:

```ts
export type ProposalStatus =
  | 'generating' | 'ready' | 'failed' | 'cancelled' | 'accepted' | 'discarded';

export interface ProposalSnapshot {
  planId: string;
  projectId: string;
  prompt: string;
  model: string;
  reasoningEffort: ReasoningEffort;
  status: ProposalStatus;
  detail: string;
  entries: PanelEntry[];          // capped tail, same PANEL_MAX_ENTRIES (300)
  plan: GeneratedRunPlan | null;  // set only when status === 'ready' | 'accepted'
  rawReply: string;
  messages: PlanChatMessage[];    // keep existing follow-up chat; plan-only for now
  revision: number;
  acceptedRunId: string | null;   // set once on accept; idempotency key
  acceptedPlan: GeneratedRunPlan | null; // exact snapshot sent to startRun
  createdAt: number;              // Date.now() at startPlan
  updatedAt: number;              // bumped on every transition/progress throttle
  endedAt?: number;
}
```

Rules:

- One row per `startPlan` call. Never update-in-place across proposals;
  concurrent `startPlan` calls create distinct `plan-<shortId>` rows.
- `images` are never persisted (existing invariant: "Never copied onto
  OrchestratorState"). Keep them in-memory on the live `PlanSession` only.
- `entries` tail-cap at 300 like `PanelSession`; persist throttled (on each
  `onChange`, debounce 250 ms or on terminal transition) so a long turn does
  not write per-token.
- `discarded` rows are tombstones hidden from list/sidebar by default
  (or hard-deleted; see §7 — builder implements tombstone + `DELETE` on
  retention sweep; list filters `status !== 'discarded'`).
- `accepted` rows remain listable (audit) but sidebar shows only
  `generating | ready | failed` (plus `cancelled`? No — see §7: cancelled is
  hidden from sidebar, visible in a future proposal drawer; sidebar shows
  exactly generating/ready/failed).

### 2. Persistence: new `proposals` table, Tracer remains sole writer

Add to `apps/desktop/src/main/trace/db.ts` `SCHEMA`:

```sql
CREATE TABLE IF NOT EXISTS proposals (
  plan_id              TEXT PRIMARY KEY,
  project_id           TEXT NOT NULL,
  prompt               TEXT NOT NULL,
  model                TEXT NOT NULL,
  reasoning_effort     TEXT NOT NULL,
  status               TEXT NOT NULL DEFAULT 'generating',
  detail               TEXT NOT NULL DEFAULT '',
  entries_json         TEXT NOT NULL DEFAULT '[]',
  plan_json            TEXT,
  raw_reply            TEXT NOT NULL DEFAULT '',
  messages_json        TEXT NOT NULL DEFAULT '[]',
  revision             INTEGER NOT NULL DEFAULT 0,
  accepted_run_id      TEXT,
  accepted_plan_json   TEXT,
  created_at           INTEGER NOT NULL,
  updated_at           INTEGER NOT NULL,
  ended_at             INTEGER
);
CREATE INDEX IF NOT EXISTS idx_proposals_project_updated
  ON proposals(project_id, updated_at DESC);
```

Add `ADDED_COLUMNS`-style migration guard for existing DBs (additive only;
never drop user data). Follow the file's existing `addMissingColumns`
pattern if the table must be added to old DBs — `CREATE TABLE IF NOT EXISTS`
already covers it, but add an explicit version comment.

Add to `apps/desktop/src/main/trace/tracer.ts` (sole writer — no other module
may `prepare` against `proposals`):

```ts
createProposal(input: { planId, projectId, prompt, model, reasoningEffort, createdAt }): void
updateProposal(planId: string, patch: Partial<{
  status, detail, entriesJson, planJson|null, rawReply, messagesJson,
  revision, acceptedRunId, acceptedPlanJson, updatedAt, endedAt
}>): void
proposal(planId: string): ProposalSnapshot | null
proposalsByProject(projectId: string, opts?: { includeDiscarded?: boolean }): ProposalSnapshot[]
```

Mapping helpers `mapProposal(row)` / `safeJson` reuse the file's existing
`safeJson`/`safeJsonArray` style. `entries`/`messages` parse defensively
(`[]` on corrupt). `plan`/`acceptedPlan` parse defensively (`null` on
corrupt, mirroring `runPlan()`).

### 3. Main service: `ProposalStore` (new file)

New file `apps/desktop/src/main/orchestrator/proposals.ts`. Owns the
in-memory live-session map + durable writes + broadcasts. Depends only on
`Tracer`-per-project accessor, `PanelRegistry<PlanStart, OrchestratorState>`,
and a `broadcast(channel, payload)` fn. Must stay import-zone clean (main
only; no renderer/preload imports; no `@earendil-works/pi-*` outside
`main/pi/`).

```ts
export interface ProposalStoreDeps {
  tracerFor(projectId: string): Tracer | null; // via registry.tracerFor(project)
  plans: PanelRegistry<PlanStart, OrchestratorState>;
  broadcast(channel: string, payload?: unknown): void;
  now?: () => number;
}

export class ProposalStore {
  start(input: PlanStart & { prompt: string; model: string }): { planId } | { error };
  onProgress(state: OrchestratorState): void;   // wired as createPlans onProgress
  list(projectId: string): ProposalSnapshot[];
  get(planId: string): ProposalSnapshot | null;
  cancel(planId: string): boolean;
  discard(planId: string): boolean;
  accept(planId: string, overrides?: { plan: GeneratedRunPlan }): Promise<
    { ok: true; runId: string } | { ok: false; issues: ValidationIssue[] }>;
  restoreOnBoot(): void;
}
```

Behaviour:

- `start()`: validate via existing `startPlan()` logic (keep `start.ts`
  validation verbatim), then `tracer.createProposal({... status:'generating'
  })` **before** `plans.start()`, then broadcast
  `IPC.eventProposalsChanged` + existing `orchestrator-progress` seed
  (`status:'running'`). Return `{ planId }`. Never cancels other sessions.
- `onProgress(state)`: map `OrchestratorState.status` →
  `ProposalStatus` (`running→generating`, `done→ready` iff `plan != null`
  else `failed`, `failed→failed`, `cancelled→cancelled`), persist throttled,
  broadcast both `orchestrator-progress` (existing, per-state) and
  `proposals-changed` (list invalidation, debounced 200 ms). Late completion
  after renderer disconnect is just a broadcast; no hook required.
- In-memory accept lock: `private acceptInFlight = new Map<string,
  Promise<...>>()` so two concurrent `accept(planId)` share one promise.
  Check `accepted_run_id` first (DB) → return `{ ok:true, runId }` without
  starting. Else call `startRun` (see §6) with the exact plan, then
  `updateProposal(accepted)` + broadcast. On `startRun` failure keep
  `status:'ready'`, do not mark accepted.
- `restoreOnBoot()`: for every known project (caller iterates projects),
  `proposalsByProject` where `status==='generating'` → set to
  `status:'failed'`, `detail:'Planning was interrupted by restart. Try again.'`,
  `endedAt: now`, broadcast. Ready/failed/cancelled/accepted rows are left
  untouched. Live `SessionRegistry` starts empty (one-shots cannot resume).
- `cancel` vs `discard` semantics (see §7).

`context.ts` wires: `this.proposals = new ProposalStore({ tracerFor,
plans, broadcast })`, passes `proposals.onProgress.bind(proposals)` into
`createPlans`, calls `restoreOnBoot()` after `registry` construction (or in
`main.ts` startup after projects load — pick one, document it; prefer
`AppContext.restoreProposals()` called from startup so tests can drive it
without Electron `app`).

`session/registry.ts`: add `list(): { id, snapshot }[]` or expose
`entries()` for boot/debug; do **not** raise `SESSION_MAX_KEPT` silently —
proposals are durable now, so the in-memory cap only bounds live turns.
Keep `SESSION_KEEP_MS`/`SESSION_MAX_KEPT` as-is; finished sessions may be
swept because the DB is the history. Document this in the file comment.

### 6. Exactly-once run creation + accepted snapshot

- Renderer never calls `runs:start` with a proposal plan directly after this
  slice (keep the channel for manual/Linear-pipeline paths). Proposal accept
  goes through `orchestrator:accept`.
- Main `ProposalStore.accept(planId, plan?)`:
  1. `get(planId)`; if missing → `{ ok:false, issues:[{where:'plan',
     message:'proposal not found'}] }`.
  2. If `accepted_run_id` set → return `{ ok:true, runId }` (idempotent,
     no second `startRun`).
  3. If `acceptInFlight.has(planId)` → return the shared promise.
  4. Else resolve the effective plan: `plan ?? stored.plan`; require
     non-null + `projectId` match; call existing `startRun(runStartDeps(ctx),
     { projectId, pipelineId: effective.pipeline.id,
       request: effective.refinedRequest, plan: effective })`.
     `startRun` already re-validates via `checkPlanRails` (round-trip guard)
     and persists `plan_json` on the run via `Tracer.startRun`.
  5. On success: `updateProposal(planId, { status:'accepted',
     acceptedRunId: runId, acceptedPlanJson: JSON.stringify(effective) })`,
     `notifyRuns`, broadcast `proposals-changed` + `runs-changed`. On failure:
     return `{ ok:false, issues }`, leave proposal `ready`.
- Tracer guarantee: "the accepted proposal becomes the persisted run plan" is
  satisfied because `registry.start` → `tracer.startRun({ plan: effective })`
  writes `plan_json` + `plan.json`. Add an assertion/test that
  `tracer.runPlan(runId)` deep-equals the accepted snapshot.

### 7. Cancellation vs discard (defined)

- `cancel(planId) → boolean`: aborts the live one-shot (`plans.cancel`),
  marks durable row `cancelled` (if terminal already, no-op, return false).
  A `cancelled` row is **retained** (audit) but hidden from the sidebar and
  not actionable (no accept/retry). `message()` on a cancelled session keeps
  its existing resume-chat rule only for accepted-plan chat, not for
  never-ready proposals.
- `discard(planId) → boolean`: if `generating`, first `cancel`, then mark
  `discarded` (tombstone; filtered from `list()` default and sidebar). If
  `ready/failed/cancelled`, mark `discarded`. If `accepted`, refuse
  (`false` — history is immutable; archiving the run is the path). Discard is
  idempotent.
- Races: `cancel` vs late `done` — `PanelSession.cancel` already guards
  terminal states; `ProposalStore.onProgress` must ignore transitions out of
  `cancelled/discarded/accepted` except the idempotent accept write. Late
  completion after `discard` is dropped (row stays `discarded`) but logged.
  `discard` vs `accept` — `accept` wins if `startRun` already launched
  (check `accepted_run_id` under the in-flight lock); otherwise `discard`
  blocks `accept` with `proposal discarded`.
- Sidebar never shows `cancelled/discarded/accepted` rows.

### 8. Activity sidebar (proposals before runs, project-scoped)

- `apps/desktop/src/shared/types.ts`: export `ProposalStatus`,
  `ProposalSnapshot` (renderer-safe; no functions). Keep
  `OrchestratorState` for live turns; `ProposalSnapshot` is the durable view.
- `apps/desktop/src/renderer/view-models/activity-runs.ts`: add

```ts
export type ActivityItem =
  | { kind: 'run'; run: RunRow }
  | { kind: 'proposal'; proposal: ProposalSnapshot };

export function selectActivityItems(
  runs: readonly RunRow[], proposals: readonly ProposalSnapshot[],
  projectId: string, recentLimit = 5,
): ActivityItem[]
```

Ordering (normative; tests pin it):

  1. `generating` proposals for `projectId`, newest `createdAt` first.
  2. Live (`running`) runs for `projectId`, newest `startedAt` first.
  3. `ready` then `failed` proposals for `projectId`, newest `updatedAt`
     first (ready before failed at equal timestamps).
  4. Finished runs for `projectId`, newest `endedAt ?? startedAt` first,
     capped at `recentLimit`.
  5. Empty `projectId` → `[]`. Cross-project rows never appear.

  Keep `selectActivityRuns` exported (back-compat for existing tests) and
  implement it as the runs-only projection of the new function.

- `apps/desktop/src/renderer/stores/run.tsx`: add
  `useActivityItems(projectId, recentLimit?)` (or extend `useActivityRuns` to
  also return proposals). It composes `useRunList(projectId,false)` +
  `useProposals(projectId)` and memoizes `selectActivityItems`. Polling
  cadence stays as-is for runs; proposals arrive via push + mount refresh.

- `apps/desktop/src/renderer/components/layout/Sidebar.tsx`: render proposal
  rows above/below runs per the ordered `ActivityItem[]` (order comes
  pre-sorted from the view-model; do not re-sort in the component). Each
  proposal row: `data-testid="sidebar-proposal-<planId>"`, status dot/ring
  (reuse `runDot`/`runDotLive` treatment: generating spins, ready solid,
  failed error colour), title = `prompt` slice + `detail`, click → open the
  proposal (Runs view, scroll to `proposal-<planId>`; do not route to
  Inspector). Keep existing `sidebar-run-*` rows, collapse behaviour, and
  `useActivityRuns` contract (extend, don't break `sidebar-activity.test.ts`
  CSS assertions).

### 9. Boot / reconnect / late completion

- Main boot: after `RunRegistry` + `ProposalStore` construction, call
  `proposals.restoreOnBoot()` for each project in `projects.list()`
  (or make `restoreOnBoot(projects)` take the list). Generating rows become
  `failed/interrupted` with retry affordance. Emit `proposals-changed` once.
- Renderer mount: `useProposals(projectId).refresh()` fetches durable rows
  (in-progress, ready, failed, unaccepted) then subscribes to
  `orchestrator-progress` + `proposals-changed`. No hook state is required to
  have been alive when generation finished (late completion works because the
  DB is the source of truth and broadcasts are global via
  `context.broadcast`, which loops all windows).
- Companion polling (`GET /v1/orchestrator/plans/:planId`) reads the durable
  `get()` so a phone also sees late completion.

## Risks / guardrails

- **Tracer sole-writer:** only `tracer.ts` prepares against `proposals`. The
  store takes a `tracerFor(projectId)` accessor; never open a second
  `better-sqlite3` handle to the same project DB.
- **In-flight accept lock is in-memory:** it dedupes concurrent accepts in one
  process (the only writer). The DB `accepted_run_id` check covers sequential
  double-accepts across restarts. Do not add a SQLite write lock or advisory
  transaction beyond the existing `better-sqlite3` transaction in `startRun`
  paths.
- **Progress write amplification:** throttle `updateProposal` on `entries`
  churn (debounce + terminal-flush). Never persist `images`.
- **Sidebar CSS contract:** `tests/renderer/sidebar-activity.test.ts` asserts
  exact classnames/animation (`runDotLive`, `spin 900ms`). Reuse the existing
  dot/ring classes for proposal rows; do not rename or restyle them.
- **Companion drift:** if list/accept are not added to HTTP, keep
  `start/state/cancel` delegating to the store so the phone sees durable
  state. Call it out in the handoff notes.
- **LinearComposer second hook instance:** fix both composers; a facade that
  only fixes `RunsScreen` leaves Linear orchestration single-session.
- **Complexity ceilings:** keep `ProposalStore` methods small; split
  mapping/persistence/broadcast helpers. JSX-heavy `RunsScreen`/`ProposalList`
  stay under 45.
