# Plan: Make Design cards directly editable and make new pipelines valid by default

## Goal

Fix the Pipelines surface in Design so that:

- A click/tap on a phase card reliably opens that phase’s settings sheet, while an actual drag only repositions the card and the card’s move/remove controls keep their existing behavior.
- A newly created pipeline is persisted with a valid hidden ID and opens ready to edit instead of immediately reporting a `lowercase kebab-case id` error.
- Newly inserted agent, command, and checkpoint phases start from complete, schema-valid defaults, so clicking **New** or **Add** does not create validation errors or warnings that the operator must clear before doing useful work.
- Rejected saves are not presented as successful saves and failed create/duplicate operations do not leave a selected “ghost” draft that was never persisted.

## Root causes found

1. `apps/desktop/src/renderer/hooks/usePipelineDraft.ts` creates new and duplicated IDs as `pipeline_${Date.now()}`. `apps/desktop/src/main/store/pipelines.ts` only accepts IDs matching `^[a-z][a-z0-9-]*$`, so the renderer immediately violates the store’s lowercase kebab-case contract with an underscore. The ID is not editable in the UI, so the operator cannot repair it.
2. The same new-pipeline constructor uses an empty description and an empty phase list, although the persisted schema requires both a non-empty description and at least one phase. The save response is ignored, so the UI moves onto a draft the store rejected.
3. `blankPhase()` in `apps/desktop/src/renderer/view-models/pipeline-view.ts` gives every new phase an empty description; command phases may point at a nonexistent `test` command, and checkpoints have an empty review question. Live validation therefore paints a brand-new card as broken before the operator has interacted with its fields.
4. `commitSave()`, `createPipeline()`, and `duplicate()` await `api.pipelines.save()` but do not inspect its `SaveResult.ok` value. A validation rejection is therefore treated like a successful save/refresh.
5. A phase card’s edit action currently depends on the inner body button’s synthetic click after the canvas has captured the pointer for click-vs-drag handling. The canvas itself should resolve the pointer gesture and open the editor when a node interaction ends without becoming a drag. Non-button portions of the card footer are also excluded wholesale by `data-canvas-control`.

## Implementation

### 1. Centralize valid pipeline and phase constructors

**File:** `apps/desktop/src/renderer/view-models/pipeline-view.ts`

- Add an exported helper for generated pipeline IDs. It must:
  - Produce a lowercase kebab ID such as `pipeline-1723456789000`, never an underscore-based ID.
  - Accept the existing pipeline IDs and add a kebab suffix (`-2`, `-3`, etc.) if the clock value collides, so tests and rapid repeated creation are deterministic.
  - Keep the ID internal; do not add an ID field to the UI.
- Move the “new pipeline” shape into an exported pure factory (for example, `newPipelineDraft`) so creation behavior is testable outside the React hook. Pass in the existing pipelines and the preferred available agent name. The returned pipeline must have:
  - The generated kebab-case ID.
  - A unique display name (`New Pipeline`, then a human-readable numbered variant).
  - A useful non-empty starter description.
  - `acceptance: { kind: 'last_phase_pass' }` and `isolation: true`.
  - One editable starter agent phase, rather than an invalid empty phase list. Use `builder` when it is available and otherwise the first available roster agent.
  - Initial canvas coordinates for the starter card.
- Extend `blankPhase()` to accept available defaults (preferred agent and configured command name) and return a complete valid phase for every kind:
  - **Agent:** unique snake-case name, non-empty explanatory description, a real available agent, the existing user prompt/input spec, and no pinned envelope.
  - **Command:** unique snake-case name and non-empty description; use the first configured project command when one exists, otherwise use a valid built-in such as `git_status` instead of a dangling `{ ref: 'test' }` warning.
  - **Checkpoint:** unique snake-case name, non-empty description, and a sensible starter question such as “Should the run continue?”.
- Keep these defaults generic and clearly editable, but ensure they satisfy the same schema and semantic validation used by the main process. Do not weaken `pipelineSchema`, remove live validation, or allow invalid pipelines into the Runs picker merely to hide the errors.

### 2. Make the draft hook honor save results and use the valid factories

**File:** `apps/desktop/src/renderer/hooks/usePipelineDraft.ts`

- Replace the inline `pipeline_${Date.now()}`/empty-pipeline construction in `createPipeline()` with the new pure factory.
- Pass roster and project-command context into every `blankPhase()` call in `insertPhase()`, so all three Add actions get valid defaults.
- Change `createPipeline()` to return success/failure (for example `Promise<boolean>`):
  - Flush the current pending edit first.
  - Save the valid fresh definition.
  - Inspect `SaveResult.ok`.
  - Only refresh app state, select the new ID, install the new draft, and set `activePhase` to the starter phase after a successful save.
  - On rejection, retain the current persisted selection and expose the returned issue messages as an operation error; never select an item that does not exist in `pipelines`.
- Replace the renderer’s hand-built duplicate (which repeats the underscore-ID defect) with `api.pipelines.duplicate(draft.id, projectId)`, after flushing pending changes. The main store already generates unique kebab `-copy` IDs. Refresh/select only when the API returns a copy; report a null/failed duplicate instead of synthesizing a ghost draft.
- Update `commitSave()` to inspect the returned `SaveResult`:
  - On `ok: false`, update the current validation issues and do not update `savedAt` or call `refreshAll()` as if persistence succeeded.
  - On `ok: true`, keep the existing saved timestamp and refresh behavior.
  - Preserve thrown-error handling, but expose a concise `actionError` string in hook state rather than only writing to `console.error`.
- Clear `actionError` when a new operation/edit starts or succeeds, and include it in the hook return type. Keep live validation as the source for errors caused by later user edits; this task removes bad constructor defaults rather than suppressing legitimate feedback.
- Ensure pending-save/selection logic still uses the server-backed pipeline list after create/duplicate and does not overwrite the newly selected draft when `refreshAll()` resolves.

### 3. Open new and existing phases directly in their editor

**File:** `apps/desktop/src/renderer/screens/PipelinesScreen.tsx`

- Keep `openPhase(index)` as the single path that both selects a phase and opens the phase `SideSheet`.
- When `createPipeline()` succeeds, open the starter phase through the same phase-sheet state so the operator lands directly in editable settings. Do not open the sheet when creation was rejected.
- Retain the existing behavior where all three Add buttons call `insertPhase()` and immediately open the new phase editor.
- Render the hook’s `actionError` as a compact `role="alert"` near the workspace actions. This is for genuine IPC/save failures, not normal initial creation.
- Continue passing the phase-specific subset of validation issues to `PhaseEditor`; with the valid factories, a newly created pipeline or phase should initially have no issue banner.

**File:** `apps/desktop/src/renderer/screens/PipelinesScreen.module.css`

- Add only the styling needed for the compact operation-error alert, using existing error/text/background tokens and without overlaying the canvas or hiding header controls.

### 4. Make canvas click-vs-drag behavior reliable across the whole card

**File:** `apps/desktop/src/renderer/components/pipeline/PipelineCanvas.tsx`

- Let the canvas pointer interaction be authoritative:
  - If a node pointer interaction ends below the movement threshold, resolve the node’s current index and call `onSelectPhase(index)` immediately from `finishInteraction()`.
  - If it exceeds the threshold, commit only the card position and suppress the follow-up click so dragging never opens settings.
  - Continue ignoring pointer starts on explicit move/remove/zoom/picker/add controls.
- Remove `data-canvas-control` from the whole `nodeActions` footer container; retain it on each actual control button. This makes non-control card/footer space behave like the rest of the card while preserving move/remove actions.
- Keep the inner card body keyboard-operable and use its `onClick` as the keyboard/synthetic-click fallback. Reuse the existing ignored-click guard so pointer-up opening does not invoke the edit path twice.
- Add a clear accessible label such as `Edit phase <name>` and a stable test hook such as `data-testid="pipeline-phase-<phase name>"` to each phase card/body. Enter/Space must open the same phase settings sheet.
- Do not change pan/zoom, card positioning persistence, execution-order controls, or drag semantics beyond reliably distinguishing a click from a drag.

**File:** `apps/desktop/src/renderer/components/pipeline/PipelineCanvas.module.css`

- Add/adjust a `:focus-visible` treatment for the phase-card edit target so keyboard users can see which card will open. Preserve the selected/error/warning borders and the draggable cursor.

### 5. Add regression coverage for valid defaults and direct editing

**File:** `apps/desktop/tests/renderer/pipeline-view.test.ts`

Add focused tests for the new pure constructors:

- Generated pipeline IDs match lowercase kebab case, contain no underscore, and receive a unique kebab suffix on collision.
- A new pipeline has a non-empty description, at least one phase, a valid starter agent, and starter canvas placement.
- `blankPhase()` still creates unique snake-case names.
- New agent, command, and checkpoint phases each have non-empty descriptions and all kind-specific required data.
- A configured command is used when supplied; otherwise the command phase uses a valid built-in and does not manufacture a missing `test` reference.
- The checkpoint default includes a non-empty question.
- Preserve the current envelope-inheritance assertion: a new agent phase must not pin an envelope override.

**File:** `apps/desktop/tests/main/store/pipeline-validate.test.ts`

- Add integration assertions that the renderer’s new-pipeline factory and each phase factory produce definitions accepted by the real `validate()` function when supplied with the corresponding agent/command context.
- Assert that the generated pipeline does not emit `id`, `description`, `phases`, missing-command, or empty-question issues. This pins the UX constructors to the actual backend contract instead of duplicating the regex only in a renderer test.
- Keep explicit tests showing that genuinely malformed user edits are still reported; the schema and validation rail remain strict.

**File:** `apps/desktop/tests/e2e/design.spec.ts` (new)

Using `seedOnboardedFixture()` and the existing Electron harness:

1. Navigate through `data-testid="nav-design"` to the Pipelines tab.
2. Click a phase card by its new stable test ID and assert that the phase `SideSheet` opens.
3. Change the phase description in the sheet and assert that the canvas card updates immediately, proving the opened settings are directly editable rather than read-only detail.
4. Use the pipeline picker’s `pipeline-new` action and assert that:
   - The newly selected pipeline has a `pipeline-...` kebab ID/test hook.
   - Its starter phase sheet opens automatically.
   - The validation tally reads `Valid` and no `lowercase kebab-case id` message or immediate error banner is visible.
5. Close the sheet, add a command and a checkpoint, and assert each new phase opens directly with no initial issue banner. The pure tests carry the detailed shape assertions; the E2E test pins the user-visible interaction.

If the generated ID is not currently observable without parsing text, add a non-visual `data-pipeline-id={pipelineId}` attribute to the existing pipeline selector trigger in `PipelineCanvas.tsx`; do not expose the internal ID as user-facing copy.

Run from the repository root:

1. `npm test -- apps/desktop/tests/renderer/pipeline-view.test.ts apps/desktop/tests/main/store/pipeline-validate.test.ts`

3. `npm run lint`

6. `npm run check`

Manual Electron check:

- Open **Design → Pipelines** and click the body or non-control footer space of several existing cards; each opens the correct phase editor on the first click.
- Drag a card by more than the click threshold; it moves without opening the sheet. Use Move earlier/later and Remove; those controls do not open the editor.
- Activate a focused card with Enter/Space and confirm the editor opens.
- Create several pipelines rapidly. Every one appears in the picker, has no kebab-ID error, starts with a valid editable phase, and remains present after switching away and back.
- Add Agent, Command, and Checkpoint phases. Each opens immediately and initially shows no validation issue; edits that actually violate a rule (for example, clearing the description or entering an invalid phase name) still produce live errors.
- Duplicate a pipeline and confirm the copy persists with a kebab `-copy` ID and can be selected/edited.
- Confirm a forced backend save rejection is not labeled Saved and does not add a nonexistent pipeline to the picker.

## Non-goals

- Do not relax the main-process pipeline schema or hide validation after the operator makes an invalid edit.
- Do not expose/edit pipeline IDs in the UI.
- Do not redesign the phase sheet, acceptance settings, Runs picker, canvas layout, or autosave debounce timing.
- Do not change Agents or Envelopes creation flows; their current constructors already begin with schema-valid identifiers/fields and are outside the reported pipeline/phase defect.
