# Plan: Orchestrator multi-build pipelines for larger tasks

## Goal

Allow the Orchestrator to take on larger bodies of work by permitting the
proposed pipeline to incorporate **multiple `build` phases and agents** as
needed for larger tasks.

- Small request → still proposes the **smallest pipeline that fulfils the
  request** (typically one build + its proof, as today).
- Larger task → may split the work across **two or more build phases or
  agents** with tight, disjoint `writes` boundaries, sequenced so later builds
  see earlier envelopes, rather than forcing all work into a single build.

Keep every existing guarantee:

1. **Each build stays proven before it is recorded** (`proof` rule: every
   build-envelope phase, and every write-capable review phase, is immediately
   followed by a configured proof code phase with `feedbackTo` naming the
   owner; `flakeRerun: 2` on proof phases).
2. **A rejection still halts the run** (`review-gates` rule:
   `verdict_consistent` + `disapproval_halts` on every review phase;
   `independent-review-before-pr` before `open_pr`; acceptance derivation
   unchanged).

No engine, IPC, trace, or renderer contract changes. This is a
prompt + composition-bullet change with test coverage. The existing rails
already loop over *every* build phase, so they already support N builds;
what changes is what the model is *told* to compose.

## Non-goals

- No new phase kind, gate, envelope, or pipeline acceptance kind.
- No change to `PhaseKind` (`agent` | `code` only). No engineer/checkpoint
  phases (the `no-engineer` rail stays).
- No change to `FIXED_ENGINE_DEFAULTS` (`envelopeRetries`, `replanAttempts`,
  `healingAttempts`, `flakeReruns`). A rejection still halts; re-planning
  still replaces failure only, budgeted at 2, never touching completed phases.
- No change to `store/pipelines.ts` `validate()`,
  `engine/preflight.ts` `preflightForRun()`, `phaseModelIssues()`,
  executor sequencing, boundary diffing, `finish()` settlement, tracer
  persistence (`run_plan`), export, IPC channels, companion HTTP, or renderer
  plan-card / transcript rendering (all pipeline-agnostic).
- No change to the cast pool (`configuredCastModels`), per-phase
  model/reasoning appointment, or the same-provider review warning (it already
  keys off the *last* build before review).
- Do not rewrite `specs/orchestrated-runs.md` (historical direction doc).
  Do not touch `apps/website/`, `apps/android/`, `resources/`, or builtin
  pipeline seeds in `apps/desktop/src/shared/builtin-pipelines.ts`.
- Do not call a model or the network in tests.

## Design

Add an explicit, guidance-only **scaling** rule and reword the intro + proof
bullet so "smallest" means "smallest that fulfils the request, at the right
scale". Enforcement stays where it is: the unchanged `proof`,
`review-gates`, `independent-review-before-pr`, `phase-model`,
`feedback-to`, and `flake-rerun` checks already validate each of N builds.

Scaling guidance to teach (bullet text is normative; see exact edits below):

- Small → one build phase + its proof (+ review/PR as the request warrants).
- Large → split into two or more build phases/agents, each with:
  - a tight `writes` boundary containing only paths its phase must touch
    (disjoint slices; synthesized implementation agents, `build` envelope,
    never a roster name; roster preferred only when purpose/envelope/boundary/
    toolProfile all fit per `prefer-roster`);
  - its own immediately-following proof code phase (`{"ref": …}`,
    `feedbackTo` = its owner, `flakeRerun: 2`, not optional);
  - sequencing so later builds consume earlier envelopes via
    `prompt.inputs` (`envelope:<phase>` must name an earlier phase — the
    existing `validate()` rail enforces direction);
  - distinct snake_case names; acceptance unchanged
    (`envelope_status` on final PR when the plan ends in PR, else
    `all_phases_pass`); review phases unchanged (both gates; read-only judge
    before `open_pr` when a write-capable finisher precedes it).

No new `check` logic is required: the scaling rule's `check` returns `[]`
(guidance only). This keeps every currently-passing plan passing and every
currently-rejected plan rejected. Do **not** add a max-builds cap, a
min-builds floor, or a disjoint-writes validator — that would be a new
rejection surface the request does not ask for.

## Exact file changes

### 1. `apps/desktop/src/main/orchestrator/composition.ts` (the only logic file)

**1a. Add a `scaling` rule.** Insert after the `proof` entry in
`COMPOSITION_RULES` (order matters: the snapshot and the id-order assertion
both enumerate it; putting it second keeps proof + scale adjacent):

```ts
{
  id: 'scaling',
  bullet:
    'Scale the pipeline to the request. For a small request propose the smallest pipeline that fulfils it, typically one build phase plus its proof. For a larger task split the work across two or more build phases or agents rather than forcing all work into a single build: give each build a tight disjoint "writes" slice, its own immediately-following proof phase with "feedbackTo" naming its owner, and sequence the builds so later ones consume earlier envelopes. Each build is proven before anything is recorded; a rejection still halts the run.',
  check: () => [],
},
```

Rationale for `check: () => []`: scale is a judgment call; the rails that
*enforce* the guarantees (`proof`, `review-gates`,
`independent-review-before-pr`, `phase-model`, `feedback-to`) already run per
phase. A guidance-only bullet cannot drift from its rail (the snapshot test
guards bullets === rails source).

**1b. Reword the `proof` bullet** so multi-build proof is explicit. Keep the
`check: proofRuleIssues` function byte-for-byte unchanged (it already loops).
Old bullet starts `Every implementation phase using a build envelope…`.
New bullet (append one sentence; keep the rest verbatim to minimise snapshot
churn):

```ts
bullet:
  'Every implementation phase using a build envelope, and every write-capable review phase, is proven before any commit. When Project commands are listed, immediately follow the agent with a code phase using one {"ref": ...} and set "feedbackTo" to the phase that owns a failure. When no Project command exists, put a configured "command_passes" gate on the agent instead. A new scaffold with no command yet is the only exception. When the pipeline has two or more implementation phases, each one gets its own immediately-following proof phase subject to the same rule.',
```

Do not touch `proofIssues`, `reviewGateIssues`,
`independentJudgeBeforePrIssues`, `reviewProviderWarnings`,
`synthesizedReviewerIssues`, `synthesizedPromptIssues`,
`inventedPathIssues`, `engineerPhaseIssues`, `generatedCompositionIssues`,

## Risks / guardrails

- **Prompt drift vs. rails:** mitigated by the snapshot test asserting bullets
  come from the same `COMPOSITION_RULES` objects the rails run. The builder
  must not hand-edit the `.snap` beyond the `-u` regeneration + diff read.
- **Over-splitting small tasks:** mitigated by keeping "smallest pipeline
  that fulfils it" as the first sentence in both the intro and the scaling
  bullet, and by leaving small goldens untouched.
- **Overlapping writes between parallel builds:** guidance says disjoint
  slices + sequential envelope chaining; no new validator is added
  deliberately (a writes-overlap rejector would be a new failure mode). The
  engine still serialises phases and diffs boundaries per phase.
- **Smith inherits the bullet:** intended — Smith designs under the same
  constitution. No Smith behavior change beyond the shared bullet text.
- **Scope creep into commits/acceptance:** generated plans in tests carry no
  `git_commit` phases; acceptance stays `all_phases_pass` (or
  `envelope_status` on final PR). The builder must not invent per-build
  commit phases or change acceptance derivation.
