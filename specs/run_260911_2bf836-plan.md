# Plan: Reorganize Settings into six discoverable categories

## Goal

Replace the desktop Settings rail’s four coarse panes with six canonical panes that separate provider connectivity, model/agent defaults, app preferences, and system housekeeping while leaving Integrations and Project independent:

| Canonical pane id | Rail label | Owns |
| --- | --- | --- |
| `providers` | `Providers` | Bridge status, subscription sign-in, direct providers, stored API keys |
| `models` | `Models & agent defaults` | Reachable/hidden model catalog, default model and reasoning, helper/healing defaults, Smith, PR writer, context/engine limits |
| `integrations` | `Integrations` | Linear and Tavily |
| `project` | `Project` | Repository identity/readiness, checks, Git, commands, setup, repository card, boundaries, scope |
| `preferences` | `Appearance & notifications` | Theme, notification alerts, dock badge, sounds |
| `system` | `System & maintenance` | Machine checks, updates, phone pairing, quit/relaunch, retention, trace compaction, leftover worktrees, app/build information, intro replay |

The rail must publish only these canonical ids through `data-testid="settings-tab-<id>"`, `data-settings-pane`, search hits, and palette hits. Old inbound pane strings must still normalize to a canonical pane.

## Non-goals and invariants

- Do not change settings storage fields, settings JSON shape, shared settings types, IPC contracts, credential storage, model discovery, project persistence, update behavior, companion behavior, or maintenance behavior.
- Do not rename section labels unless called out below. Existing `Section` labels are the `data-sec` contract used by search jumps; retaining them preserves stable ids such as `api-keys`, `appearance`, `smith`, and `retention`.
- Do not add a route migration or persisted-data migration. Pane ids are renderer navigation state, and compatibility is handled at normalization boundaries.
- Do not remove or rename existing control-level testids (`settings-theme-*`, provider cards/key rows, settings search/palette inputs, etc.). Rail testids continue to use the existing template with the new canonical id.
- Do not change the Smith artifact/proposal fixtures whose unrelated section id happens to be `models`; only Settings navigation identifiers are in scope.
- Do not touch `apps/website/` or `apps/android/`.

## Exact navigation and compatibility contract

### Canonical pane order

Use this exact order everywhere panes are enumerated:

```ts
['providers', 'models', 'integrations', 'project', 'preferences', 'system']
```

### Rail groups

In `SettingsScreen.tsx`, use three visible groups:

```ts
const RAIL_GROUPS = [
  { label: 'Agent runtime', items: ['providers', 'models'] },
  { label: 'Workspace', items: ['integrations', 'project'] },
  { label: 'Application', items: ['preferences', 'system'] },
];
```

This keeps related pairs adjacent without placing all six under the redundant single heading `Settings`.

### Legacy normalization

Add one exported normalization helper in `apps/desktop/src/renderer/view-models/settings-search.tsx` and make `SettingsScreen`’s `normalizePane()` delegate to it. The app shell must use the same helper whenever an external component opens Settings, so the screen, `data-settings-pane`, Smith screen context, and automation marker never disagree.

Map exact values as follows:

| Inbound value | Canonical result | Reason |
| --- | --- | --- |
| `providers` | `providers` | canonical |
| `models` | `models` | canonical and sensible destination for the old mixed Models & Providers pane |
| `defaults` | `models` | old internal agent-default grouping |
| `integrations` | `integrations` | unchanged canonical id |
| `project` | `project` | unchanged canonical id |
| `project-commands` | `project` | existing doctor deep link |
| `preferences` | `preferences` | canonical |
| `app` | `preferences` | old default App pane now lands on user-facing app preferences |
| `general` | `preferences` | old general/preferences alias |
| `system` | `system` | canonical |
| `maintenance` | `system` | old maintenance grouping |
| `about` | `system` | old app/build information grouping |
| any unknown string | `preferences` | safe canonical default rather than producing an unrendered pane |

Keep `models` as the canonical model/defaults id; update live provider remediation links to `providers` rather than trying to reinterpret every inbound `models` value as a provider link.

## Files and exact changes

### 1. `apps/desktop/src/renderer/view-models/settings-search.tsx`

#### Pane types and metadata

- Change `SettingsPaneId` to the six-id union:

  ```ts
  export type SettingsPaneId =
    | 'providers'
    | 'models'
    | 'integrations'
    | 'project'
    | 'preferences'
    | 'system';
  ```

- Replace the four entries in `SETTINGS_PANES` with six entries in the canonical order above.
- Use these labels and concerns in the metadata:
  - `providers`: label `Providers`; hint describing Bridge, subscriptions, API keys, and direct provider connections; keywords including provider names, Bridge/connect/OAuth/subscription, API key/token/credential.
  - `models`: label `Models & agent defaults`; hint describing model catalog, defaults, reasoning, Smith, and context limits; keywords including model/catalog/hide/reachable, default/helper/healing, reasoning effort, Smith/chat, PR writer, compaction/context/retries.
  - `integrations`: retain the current label and Linear/Tavily-oriented hint/keywords.
  - `project`: retain the current label and repository/Git/commands/boundaries-oriented hint/keywords.
  - `preferences`: label `Appearance & notifications`; hint describing themes, alerts, dock badge, and sounds; keywords including all theme names plus notification/alert/audio terms.
  - `system`: label `System & maintenance`; hint describing checks, updates, phone, lifecycle, retention, cleanup, and build information; keywords including doctor/diagnostics, update/version, companion/pairing, quit/relaunch, retention/trace/database, orphan/worktree, build/about/intro.

#### Section registry

- Remove `LegacySettingsPaneId` and the `currentPane()` folding layer. `SettingsSectionRef.pane` should be `SettingsPaneId`, and every section should name its actual rendered canonical pane.
- Preserve existing section labels and notes, but assign them exactly as follows:
  - `providers`: `Providers`, `Subscriptions`, `API keys`.
  - `models`: `Models`, `Agent defaults`, `Model`, `Helper tasks`, `Healing`, `Smith`, `Pull requests`, `Advanced`.
  - `integrations`: `Linear`, `Tavily`.
  - `project`: `Project`, `Readiness`, `Checks`, `Git`, `Commands`, `Setup`, `Repository card`, `Boundaries`, `Scope`.
  - `preferences`: `Appearance`, `Notifications`.
  - `system`: `Checks`, `Software updates`, `Phone`, `Application`, `Retention`, `Leftover worktrees`, `Foundry`, `Build`, `Elsewhere`.
- Keep the section keywords broad enough that old vocabulary still finds the moved setting. In particular:
  - provider/API-key terms must return `providers`;
  - model/reasoning/Smith/context terms must return `models`;
  - theme/notification/sound terms must return `preferences`;
  - doctor/update/phone/retention/worktree/version/about terms must return `system`.
- Update stale comments that refer to `General`, four panes, or legacy group folding. Update the toggle comment from `General → Notifications` to `Appearance & notifications → Notifications`.

#### Normalization and search

- Export a `normalizeSettingsPane(value: string): SettingsPaneId` helper implementing the exact compatibility table above. Use a typed alias map plus a canonical-id check; do not use `any`.
- Delete `currentPane()`. `searchSettings()` should use `section.pane` directly for the hit’s pane and pane label.
- Preserve the current scoring rules: exact section title, prefix, title substring, keywords, then note; pane keyword-only hits remain behind section-title hits. This keeps `api key` landing on the `API keys` section before the Providers pane-level result.
- Keep `sectionId()`, the cap behavior, highlighting, and `paneMatchesQuery()` API unchanged apart from the larger pane union.

### 2. `apps/desktop/src/renderer/screens/SettingsScreen.tsx`

#### Pane declarations and normalization

- Import `normalizeSettingsPane` from the search view-model.
- Keep the local `Pane = SettingsPaneId` alias, but make `normalizePane(value)` return `normalizeSettingsPane(value)` so direct renders with legacy strings remain compatible.
- Replace `PANES` with these exact literals in canonical order:

  ```ts
  [
    { id: 'providers', label: 'Providers' },
    { id: 'models', label: 'Models & agent defaults' },
    { id: 'integrations', label: 'Integrations' },
    { id: 'project', label: 'Project' },
    { id: 'preferences', label: 'Appearance & notifications' },
    { id: 'system', label: 'System & maintenance' },
  ]
  ```

- Replace the single `Settings` rail group with the three exact `RAIL_GROUPS` from the contract above.
- Narrow the `onPaneChange` prop to `(pane: SettingsPaneId) => void`; only canonical ids should be emitted from tab clicks or search/palette jumps.

#### Re-home rendered sections

Split the existing mixed conditional blocks without changing the controls inside each section:

1. `pane === 'providers'` renders only `Providers`, `Subscriptions`, and `API keys`.
2. `pane === 'models'` begins with `Models`, then renders `Agent defaults`, `Model`, `Helper tasks`, `Healing`, `Smith`, `Pull requests`, and `Advanced`.
3. `pane === 'integrations'` remains Linear and Tavily.
4. `pane === 'project'` remains the full Project surface.
5. `pane === 'preferences'` renders `Appearance` and `Notifications` only.
6. `pane === 'system'` renders, in order: `Checks`, `Software updates`, `Phone`, `Application`, `Retention`, `Leftover worktrees`, `Foundry`, `Build`, and `Elsewhere`.

Specific follow-up edits inside the screen:

- Change the orphan-loading effect from `pane === 'app'` to `pane === 'system'`.
- In the `Elsewhere` section, change `Manage providers` from `setPaneLive('models')` to `setPaneLive('providers')`.
- Both `DoctorList` callbacks must normalize their string argument before calling `setPaneLive`; replace unsafe `next as Pane` casts with `setPaneLive(normalizePane(next))`. This protects old `maintenance`/`project-commands` values as well as future external aliases.
- Preserve every `Section label` exactly. Because `Section` continues to stamp `data-sec={sectionId(label)}`, search results can switch to the canonical pane and then use the existing `scrollTargetRef`/`flashSection` effect to scroll after the new pane paints.
- Do not duplicate a section in two panes. Duplicate labels such as `Checks` are safe because only one pane body is mounted at a time, and search hits include the target pane.
- Keep `jumpTo`, `scrollTargetRef`, `requestAnimationFrame`, and the flash behavior structurally unchanged; only canonical target panes should flow into them.

## Risks and guardrails

- **Screen/marker disagreement:** avoid by using one shared normalizer in both App and SettingsScreen; never store a legacy id in App state.
- **Provider fixes landing on models:** update main doctor fix values to `providers`; preserving `models` as a canonical pane does not preserve the old provider meaning.
- **Section jump drift:** move whole existing `Section` blocks and keep their labels unchanged. Registry pane ownership and rendered pane ownership must be edited together.
- **Duplicate `Checks` ids:** safe only because Project and System are mutually exclusive pane bodies. Do not render both pane bodies simultaneously.
- **Hidden maintenance data:** change orphan loading to `system`; otherwise the moved worktree section could display stale/empty state.
- **Cross-link drift:** update Sidebar, App normalization, Runs phone pill, doctor fixes, and Elsewhere’s Manage providers button together.
- **Responsive crowding:** retain horizontal overflow and add inter-group spacing/fixed group width only in the existing narrow media query.
- **Accidental persistence work:** pane ids remain renderer navigation state. Any proposed store migration, IPC change, or settings schema edit is out of scope.
