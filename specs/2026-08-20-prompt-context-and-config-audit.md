# Audit: Prompt/Context Engineering and Configuration Surface

**Date:** 2026-08-20 · **Scope:** read-only audit, no code changed · **Repo state:** `main` @ `c12a3a4`

Goal: make Foundry (1) faster and better at its core job — leaner, higher-signal prompts and context per phase — and (2) simpler to configure and understand — fewer clicks, fewer decisions, clearer mental models in Settings, pipeline/agent configuration, and onboarding.

All findings cite current files and behavior. Repo invariants (fail-closed phases, Tracer as sole SQLite writer, worktree isolation, main-owns-privilege, the pi import boundary) are treated as fixed; every proposal below respects them. Where a claim about runtime behavior could not be verified statically it is marked **(assumption)**.

---

## Executive summary

Foundry's prompt machinery is unusually disciplined — one zod schema drives the example, the tool schema, the wire constraint, and the parse; corrections are short deltas, not full re-renders; the static prompt surface is lean (harness ~350 chars, roster prompts 600–1,900 chars). The biggest wins are therefore not "trim the prompts" but **fix what's missing, delete what's contradictory, and shrink the configuration surface around it**:

1. **Agents get zero repo context and zero diff context.** Discovery is deliberately off (`noContextFiles`, `pi/open-session.ts`), and nothing replaces it: every phase, in its own fresh session, re-discovers the stack, conventions, and layout with tool calls — the single largest avoidable cost per run, in both tokens and latency. Reviewer, finisher, pr_writer, and documenter are told to "inspect the diff" but receive no changed-file list, no branch point, no diff stat, even though the engine computes all of it (`engine/boundary.ts`). **Proposal: an engine-owned, once-per-project "project card" plus a per-phase git context block** (§R1, §R2). Highest impact item in this report.

2. **The envelope shape reaches the model three ways per turn** (prompt example + `submit_envelope` tool schema + `outputFormat` json_schema), and the instruction to use it is stated three times (harness, `## Report` block, tool description) — while every correction message _contradicts_ the tool channel ("Reply again with ONLY this JSON object, no prose"). Unify on the tool channel and cut the redundancy (§R3, §R4).

3. **The refined request never reaches the phases that need it.** In `ship-pr`/`sdlc-pr`, `refine` produces `improved_request` and only `plan` sees it; build, production_check, review, and open_pr all get the raw request again (§F1.6). One-line pipeline fix with outsized quality impact (§R5).

4. **Settings is ~35 controls across 6 panes; ~6 matter.** One setting is fully dead (`appearance`), one is renderer-only (`pollCadenceMs`), one is a global key hidden inside the per-project pane (`detectModel`), three retry knobs interact with no stated model, one section has zero controls ("Autonomy"), and `bridgePort` exists even though the manager already scans a band. With no back-compat constraint, Settings can collapse to **3 panes and ~15 controls** (§R7).

5. **The pipeline/agent schema carries dead and unusable knobs**: `tools`/`disabledTools`/`toolProfile` exist in both agent and phase schemas with no UI and no consumer; `command_passes` can be added in the UI but never configured, guaranteeing a validation error; `resetToBuiltins` IPC has no caller; `prompt.template` has exactly one value; builtin phases redundantly restate their agent's envelope. Delete or wire each (§R8–R10).

6. **Onboarding spends three of six screens teaching vocabulary the app could stop needing.** "Envelope" and "gate" leak everywhere; merge/landing is undiscoverable until a run finishes. Compress the concept screens, rename the two leakiest terms in operator-facing copy, and let the first run's Inspector teach by showing (§R14–R16).

Estimated aggregate effect **(assumption — static estimate, no runtime measurement)**: R1–R6 remove roughly 800–2,000 tokens of redundancy per agent phase and eliminate the repeated exploratory tool-call tax (typically the first 5–15 tool calls of every phase), while R7–R16 cut the operator-facing decision surface by more than half without removing any capability that a shipped pipeline actually uses.

## Area 1 — Prompt and context assembly

### How it works today (verified)

- `engine/prompts.ts:renderPrompt()` renders the roster agent's system + user templates, appends declared-but-unreferenced `phase.prompt.inputs` as sections, then appends a `## Report` block with a schema-derived JSON example (`engine/envelopes.ts:exampleFor`).
- The system role is three layers: `FOUNDRY_RUN_HARNESS` (`pi/system-prompt.ts`) replaces pi's persona; the roster system prompt is appended per turn via `before_agent_start` (`pi/policy-extension.ts:37-43`); discovery is fully off (`pi/open-session.ts` — `noContextFiles` etc.), so **no AGENTS.md/README ever enters context**.
- Every agent phase gets all ten tools (`pi/pi-transport.ts:130`): the seven builtins plus `report_progress`, `read_phase_context`, `submit_envelope`. The envelope schema also rides as `outputFormat: {type:'json_schema'}` (`engine/runners/agent.ts:216-219`).
- Context flows phase-to-phase **only** as declared envelope inputs (pretty JSON) plus the on-demand `read_phase_context` chain; sessions are per-agent and run-long; compaction is between phases at 80% (`executor.ts:compactFullSessions`, `settings.ts:compactionThreshold`).
- Corrections are short deltas into the live session (`correctionMessage`, `gateCorrection`, `boundaryCorrection`); a `feedbackTo` loop re-renders and re-sends the **entire** phase prompt (`runners/agent.ts:run` re-entered via goto).

### Findings

**F1.1 — No repo conventions ever reach an agent.** `noContextFiles: true` plus nothing injected in `prompts.ts`. Refiner is told "Skim the repo first: README, top-level layout, manifests" (`store/builtin-agents.ts`); finisher is told to match "the conventions already in this codebase" — each must burn tool calls to find them, **per agent, per run**, because builder/reviewer/finisher are separate sessions. Foundry already runs one-shot detection and readiness against the repo and stores per-project commands (`store/projects.ts:commands`) — the raw material for a project summary exists; it is just never assembled for run agents.

**F1.2 — No git context for the phases whose whole job is the diff.** reviewer/finisher/pr_writer/documenter prompts say "inspect the worktree diff" / "Inspect the diff against the base branch" (`store/builtin-agents.ts`), but the prompt contains no changed-file list, no branch-point SHA, no diff stat. `{{branch}}`/`{{base_ref}}` exist in the palette (`prompts.ts:29-46`) and **no builtin uses them**, so pr_writer must discover the base ref itself with shell calls. The engine computes exactly this data post-phase in `boundary.enforce()` and holds `branchPointSha`.

**F1.3 — Envelope shape ×3, envelope instruction ×3, and a contradiction.** Per turn the shape is present as (a) the `## Report` example JSON (~300–700 chars), (b) the `submit_envelope` parameters schema, (c) the `outputFormat` constraint. The "call submit_envelope once… Foundry validates" instruction appears in the harness, the `## Report` block, and the tool description. Meanwhile every correction path instructs a **text** reply: `correctionMessage` — "Reply again with ONLY this JSON object, no prose, no code fence" (`envelopes.ts:377-390`); `gateCorrection` — "reply again with the envelope JSON only" (`gates.ts:262-270`); `boundaryCorrection` similarly (`boundary.ts:158-166`). Both channels parse (structured first, text fallback, `runners/agent.ts:envelopeFrom`), so this works — but the model is being told two different things, and the full example JSON is regenerated into **every** envelope correction.

**F1.4 — "You are read-only" while holding write tools.** Refiner, scout, reviewer, pr_writer, issue_writer say "You are read-only. Do not create, edit, or delete any file" yet run with `edit`, `write`, `bash` registered; enforcement is the tool_call policy plus post-hoc git revert. The instruction and the tool surface disagree. The pi layer already has the machinery for real narrowing (`READ_ONLY_TOOLS`, and the AGENTS.md invariant "Read-only means no write tool exists" — currently honored only by one-shots), and the roster/phase schemas already declare `tools`/`toolProfile` fields that nothing consumes (§F3.1). Note the comment at `runners/agent.ts:236-238` claims per-phase tool narrowing ("effectiveDisabledToolIds") that does not exist in the wiring — a stale comment.

**F1.5 — The `.foundry-handoff/` mechanism is vestigial.** The engine only mkdirs the directory and lists it into `{{handoff_files}}`; the envelope handoff copy is written to the **trace** dir (`runners/agent.ts:writeHandoff` → `handoff/<phase>.json` in the run's trace), not the worktree. Only planner's write boundary even names `.foundry-handoff/`; **no builtin pipeline declares `handoff_files` as an input** and no builtin prompt uses `{{handoff_dir}}`. Two template tokens, a boundary carve-out (`boundary.ts:168`), and a directory per worktree exist to serve a path nothing shipped uses.

**F1.6 — The refined brief dies after `plan`.** In `ship-pr`/`sdlc-pr`, `envelope:refine` is an input only to `plan` (`store/builtin-pipelines.ts:53`); build, production_check, review, document, and open_pr receive the **raw** `{{request}}` again. The refiner's own copy says "It must stand alone: whoever reads it never sees the draft" — but every downstream phase sees only the draft.

**F1.7 — `feedbackTo` re-sends the whole phase prompt into a session that already has it.** A red `test` phase jumps back to `build`; `runner.run()` re-renders request + declared envelopes + `## Report` + the feedback section and sends all of it into the same live session that already contains the identical prompt. Envelope/gate corrections got this right (delta-only); the feedback loop did not. On a large plan envelope this re-sends the largest block in the run, once per feedback retry (default budget 2).

**F1.8 — One-shot prompt debris.**

- `DETECT_TOOLS = ['Read','Grep','Glob','LS']` (`engine/detect.ts:471`) is capitalized, matches no pi tool name, and is unused (sessions use `READ_ONLY_TOOLS`); it also leaks into `engine/AGENTS.md` prose.
- The readiness marker-ignore rule is stated three times (twice in `READINESS_SYSTEM_PROMPT`, once in every user prompt, `readiness/prompt.ts`), and the system prompt instructs "Fan out. Use general sub-agents/workers…" — **no sub-agent/task tool exists in the session's registry**; the instruction is unactionable.
- The run-start command fill (`engine/operations.ts:88-100`) reuses `DETECT_PROMPT` but omits the manifest-sniff context the interactive `DetectSession` includes — the fill agent works with strictly less context than the Settings flow, at the moment it matters most (first run).

**F1.9 — SHELL_NOTE half-truths.** "You inherit the operator's shell environment: PATH, toolchains, and credentials are already live" (`store/builtin-agents.ts:12-16`) — a fresh worktree has run only `setupScript`; toolchains are live only if setup installed them, and the note is appended even to read-only agents told not to run write commands. Meanwhile nothing tells the agent what setup actually ran or whether it succeeded.

**F1.10 — Unbounded envelope fields.** `summary` and `notes_for_next_agent` are unbounded strings (`engine/envelopes.ts:base`); a `review.findings` array can grow arbitrarily. These get pretty-printed (2-space indent) into every downstream prompt that declares them — `sdlc-pr`'s open_pr inlines **five** envelopes. Gate/feedback tails are already bounded (1,000 / 4,000 chars); envelope prose is not.

**F1.11 — What is already good (do not churn).** The schema-derived example/constraint/parse triad; delta-only envelope/gate corrections; separate envelope-vs-gate budgets; rewind-after-N-corrections dropping failed attempts from context; per-turn fresh envelope tool (validator-cache correctness); trace-recorded prompts (`<agent>/prompts/<phase>-1.md`). These are the right shape.

## Area 2 — Settings UI and config stores

### How it works today (verified)

`SettingsScreen.tsx` (2,424 lines) renders 6 panes — General / Providers / Agent defaults / Project / Maintenance / About — over `store/settings.ts` (23 keys) and `store/projects.ts` (per-project: `baseRef`, `mergePolicy`, `commands`, `setupScript`, `protectedPaths`, `isolation`, `scaffold`, scope flags). Everything autosaves; credentials never live in settings (store AGENTS.md rule).

### Findings

**F2.1 — Dead and renderer-only settings.**

- `appearance` (`'system' | 'dark'`, `settings.ts:53`): **no UI control, no consumer anywhere** (grep: schema, default, type, mock only). Fully dead.
- `pollCadenceMs`: has a UI control ("Trace poll cadence (ms)") but no main-process consumer; only `renderer/stores/run.tsx:81` reads it, and the non-live cadence (3000) is already hardcoded there without a setting.
- Project `isolation` (default true): consumed at `executor.ts:172,306` but settable in **no UI** — pipelines expose an isolation toggle; projects don't. A schema field no operator can change.

**F2.2 — Misplaced and half-merged.** `detectModel` is a **global** key edited only inside Settings → Project → Commands ("Who answers 'Ask AI'"), and detection already borrows the global `defaultReasoningEffort` (`operations.ts:94`) — it is half-merged into defaults already. `readinessModel`/`readinessReasoningEffort` are a second such pair.

**F2.3 — Three retry knobs, no stated interaction.** `envelopeRetries` (0–5), `gateRetries` (0–5, and note `phase.retries` in every builtin pipeline overrides it to 2 anyway), `rewindAfterCorrections` (0–20, whose own schema comment says the useful range "stops well before a phase's retry budgets", `settings.ts:41`). An operator cannot form a model of how these interact from the UI; the hints define mechanics using undefined terms ("Envelope retries — Correction messages sent when a reply will not parse").

**F2.4 — Sections that exist to explain, not to configure.** "Autonomy" contains zero controls (SettingsScreen.tsx:1596-1604 — prose only). "Transport" exists for one number (`bridgePort`) whose hint admits the manager scans the 37700–37799 band when busy. Two panes render the same global `DoctorList` ("Checks") with different notes; "Refresh models" appears twice.

**F2.5 — Opaque copy.** "Turn timeout (minutes)" has **no hint at all**; "envelope", "vendored provider Bridge", "compact context", and "corrections" are used in hints without definition. Scope is a read-only section whose action lives on another screen ("Change scope in Design (⌘3)…").

**F2.6 — The decision surface vs. the real surface.** A fresh setup needs ~9–14 clicks and 5–8 decisions (provider, repo, commands, setup script, readiness) — but the operator _faces_ ~35 controls across 6 panes to learn they can skip ~29 of them. The cost is not clicks; it is evaluation.

**F2.7 — Good bones.** Validated-on-change with inline errors; atomic JSON writes; normalize-on-read migration; auto-save with no Save button; the "no credential is a setting" rule; the ⌘K settings palette. Keep all of it.

## Area 3 — Pipeline/agent configuration model

### How it works today (verified)

9 builtin agents (`store/builtin-agents.ts`), 6 builtin pipelines (`store/builtin-pipelines.ts`), 6 gates (`engine/gates.ts`), 9 envelope kinds, 4 acceptance kinds, 3 phase kinds. Operators can create/edit/duplicate/fork/delete agents and pipelines (builtins fork-on-rename, self-restore on delete-from-JSON, never clobbered by upgrades). A run takes exactly three operator decisions: request, pipeline, start (`types.ts:StartRunInput`; `RunsScreen.tsx`).

### Findings

**F3.1 — Dead schema knobs.** `tools`, `disabledTools`, `toolProfile` exist in both `agentSchema` (`roster.ts:44-48`) and `phaseSchema` (`pipelines.ts:53-57`) with **no UI, no engine consumer, no builtin usage** — plus an empty `{/* ── system tools ── */}` placeholder in RosterScreen. Either these become the mechanism for F1.4's real read-only narrowing, or they should be deleted; today they are pure surface.

**F3.2 — A UI trap.** The PhaseEditor lets an operator add the `command_passes` gate from the catalog but offers no field for its required `config.argv`, so a UI-added `command_passes` **always** fails validation ("command_passes needs a configured command", `pipelines.ts` validate). A configuration path that can only produce an error.

**F3.3 — Knobs with exactly one value in practice.** `prompt.template` (`'user'` everywhere; PhaseEditor hardcodes the label "template: user"). All 6 builtin pipelines use the same acceptance kind (`envelope_status` on `open_pr`); `phase_flag`/`all_phases_pass`/`last_phase_pass` have zero shipped uses. `timeoutMs` (non-engineer), `optional`, per-phase `model`/`envelope` overrides, `argv` commands, `git_status`/`noop` builtins, `engineer` phases: zero shipped uses. Every builtin agent-phase `retries` is 2; every `feedbackRetries` is 2.

**F3.4 — Redundant restatement.** Every builtin phase sets `envelope` equal to its agent's envelope (e.g. `refinePhase()` sets `envelope: 'brief'`, refiner already declares `brief`) even though the engine resolves `phase.envelope ?? agent.envelope` — the shipped data teaches editors that the field is required when it is an override.

**F3.5 — Unreachable reset; unversioned builtins.** `resetToBuiltins` exists as IPC (`ipc/roster.ts:71`, `ipc/pipelines.ts:113`) with **no renderer caller** outside the mock. And because builtins are seeds ("user-edited copies are never overwritten"), an operator who once edited `builder` keeps a stale prompt forever with no in-app way to see or adopt the shipped update.

**F3.6 — Vocabulary leakage is partial.** Phase kinds are already softened for operators (`agent`/`command`/`checkpoint`, `utils/derive.ts:68-72`) — the right pattern. But "envelope" and "gate" appear verbatim across Roster ("Envelope kind — The typed reply this agent must return"), PhaseEditor, acceptance labels, Inspector badges, Smith cards, and empty states ("orchestrate bounded agent phases and command gates").

**F3.7 — The per-run surface is already minimal.** Request + pipeline + start, with preflight rails (validation, missing-command detection, readiness banner, base sync). This is the model the rest of the app should converge toward.

## Area 4 — Onboarding and in-app explanation

### How it works today (verified)

Six steps (`onboarding/shared.tsx:10-17`): Welcome → Factory → Roster → Providers (gated on a usable model) → Doctor (gated on blocking checks) → Project (gated on a selected repo). Three of six are purely conceptual. First run then needs request + pipeline + Start; a new project additionally passes through command detection (`DetectionPanel`), setup-script generation, and the readiness flow (11 criteria, `Check → Fix → Verify → PR → Merge`).

### Findings

**F4.1 — Three screens teach what one could.** Welcome, Factory, and Roster all restate the same triad ("typed envelope", "gates leave evidence", "isolated worktree") — RosterScreen's clarify line repeats FactoryScreen's lead nearly verbatim. Meanwhile the concepts an operator will actually collide with first — command detection, setup script, readiness, merge — get zero onboarding mention ("Missing test commands are detected automatically when you start" first appears on the Runs empty state).

**F4.2 — Jargon without definition at the moment of use.** "Envelopes and gates decide success" (Welcome, before either is defined); "in-process on pi", "bridge on {port}" (Providers); "gates 4/4" in the Project screen's decorative SVG; "usable model" defined only tautologically; "signals" in Doctor telemetry (internal `checks.length`).

**F4.3 — Merge/landing is undiscoverable.** Onboarding promises "merge on your terms" but where worktrees live, what a branch is named, and how work lands (`OutcomeBanner`: Merge / Fix with agent (rebase) / Discard / Create PR, `RunDetailScreen.tsx:61-92`) are only discoverable after a run finishes. Nothing bridges "run accepted" to "so where is my code?" for a first-time operator.

**F4.4 — The readiness flow is the heaviest first-project step** — 11 criteria, a five-stage stepper, its own model picker, and skip-with-double-confirm — presented before the operator has seen a single run. Its copy is accurate and its states are well-labeled (verified in `ReadinessFlow.tsx`, `readiness-view.ts`); the issue is sequencing and volume, not quality.

**F4.5 — Good copy worth keeping**: the trust statements ("Foundry never writes to your working tree — only to worktrees it creates"), the DetectionPanel's rejected-vs-unrunnable distinction, the Runs/PR empty states that point at the next action.

## Considered and rejected

- **Re-enabling pi's context-file discovery (`noContextFiles: false`) instead of R1.** Rejected: it violates the explicit pi/AGENTS.md invariant ("ancestor AGENTS.md / .pi/SYSTEM.md must not change what a run does") and would make run behavior depend on uncontrolled repo files. The project card keeps control in the engine.
- **A retrieval/embedding index of the repo for phase context.** Rejected: adds a dependency (charter forbids), a stale-index problem across worktrees, and the project card + the agent's own tools cover the need at far lower complexity.
- **One shared session for all agents in a run** (to stop re-discovery). Rejected: destroys per-agent boundary attribution, rewind anchoring (`PhaseRewinder` is per-phase per-session), and the roster-role-as-system-prompt model; compaction would also hit one giant context. R1 solves the same problem without touching sequencing invariants.
- **Dropping the `submit_envelope` tool and relying on `outputFormat` alone.** Rejected: the tool call is the primary structured channel today and `outputFormat` support may vary by provider **(assumption — vendor behavior not verifiable statically from the pinned docs alone)**; the text-parse fallback exists precisely because neither channel is universal. R3 removes redundancy without removing a channel.
- **Denormalizing per-run cost/usage into settings-visible summaries** while touching Settings. Rejected outright: `trace/AGENTS.md` forbids denormalized totals; usage stays event-derived.
- **Auto-adopting updated builtin prompts on upgrade.** Rejected: violates "builtins are seeds; user-edited copies are never overwritten." R10's opt-in badge + reset achieves the goal within the invariant.
- **Removing the `.foundry-handoff/` directory entirely as a quick win.** Deferred to M-effort rather than rejected: planner's write boundary, `boundary.ts`'s rewind carve-out, executor mkdir/resume paths, and the template tokens all reference it; ripping it out safely needs an executor test pass. The quick win is only to stop advertising it (QW12).
- **Removing gates or acceptance kinds from the engine.** Rejected: they are cheap in code, invisible per-run, and the fail-closed design depends on them; the problem is UI exposure (R9, R15), not the mechanism.
- **Collapsing per-agent sessions' `read_phase_context` to a filtered/paginated API.** Considered for token control; rejected for now: envelopes are small in practice once R11 caps prose, and the whole-chain dump is a deliberate escape hatch. Revisit only if traces show large chains being pulled repeatedly **(assumption)**.
- **Moving readiness entirely out of the product.** Rejected: its checks are the substrate for R1's project card and the marker-file contract is used by pipelines' success odds; R16 resequences it instead.
