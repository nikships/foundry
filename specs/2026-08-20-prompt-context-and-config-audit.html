Audit & Remaining Opportunities

Foundry can be faster, and easier to understand.

This is an audit of how Foundry builds the prompts and context each agent phase receives, and how much of its configuration surface an operator actually needs. Most initial findings (project cards, git context, 3-pane settings, 4-step onboarding, brief propagation) have landed in main — this document tracks the remaining open items.

1Prompts & context assembly

What each agent phase is told, and what it actually gets to see.

How it works today

Each phase renders an agent's system + user prompt templates with project context cards and git diff context injected. Sessions are per-agent and run-long; compaction runs between phases at 80% full. Corrections are short deltas; but a failed-test feedback loop still re-sends the whole prompt.

F1.4

"You are read-only" while holding write tools

Five agents are told not to touch files, yet they hold edit / write / bash. Enforcement is policy + post-hoc git revert — not the tool surface.
▶

Refiner, scout, reviewer, pr_writer, issue_writer all say "do not create, edit, or delete any file" while still having write tools registered. The read-only machinery already exists for one-shots (a read-only session simply has no write tool in its registry). A comment in the runner claims per-phase tool narrowing that does not exist in the wiring.

Resolved (#168). toolProfile: 'read-only' now opens the run session with the read subset, so edit / write / bash do not exist for those five agents, and a Foundry-owned git_diff tool replaces the shell they used to inspect a diff with.

F1.5

The handoff-folder mechanism is vestigial

The engine makes the folder and lists it, but no shipped pipeline or prompt uses it. Envelopes actually flow through the trace, not this folder.
▶

The engine only creates the .foundry-handoff/ directory and lists its contents into a token. The real envelope handoff is written to the trace folder, not the worktree. Only the planner's write boundary even names the folder; no builtin pipeline declares handoff files as an input. Two template tokens, a boundary carve-out, and a directory per worktree exist to serve a path nothing shipped uses.

F1.7

The feedback loop re-sends the whole prompt

A red test jumps back to build and re-renders the entire phase prompt into the same session that already holds it.
▶

Envelope and gate corrections got this right — they're short deltas. The failed-test feedback loop did not: it re-renders request + declared envelopes + the answer block + the feedback section, and sends all of it again. On a large plan envelope this re-sends the biggest block in the run, once per feedback retry (default 2).

Resolved (#167). A re-entry whose live session still holds the rendered prompt now sends only the feedback evidence. A prompt ledger keyed on the session object forgets on compaction, rewind, close, and replacement, so every uncertainty falls back to the full prompt.

F1.10

What's already good — keep it

The schema-driven example/constraint/parse triad; delta-only corrections; separate retry budgets; rewind-after-N; per-turn fresh envelope tool; trace-recorded prompts.
▶

One validation schema drives the answer example, the tool schema, the output constraint, and the parse — so they cannot drift. Corrections are short deltas into the live session. Envelope and gate retry budgets are separate. Rewind-after-N drops failed attempts from context. The envelope tool is rebuilt fresh per turn (validator-cache correctness). Every prompt is written to the trace for inspection. These are the right shape — don't churn them.

2Pipelines & agents

Whether the configuration model is more adjustable than it needs to be.

How it works today

Built-in agents and pipelines ship with update-diff badges and reset affordances; invalid command_passes gates are removed from UI catalogs; phase envelope restatements are cleaned up. What remains are unused tool schema fields and leaked terminology.

F3.1

Dead schema knobs

tools / disabledTools / toolProfile exist on both agents and phases with no UI, no engine consumer, and no builtin usage.
▶

There's even an empty {/* ── system tools ── */} placeholder in the roster editor waiting for a UI that never arrived. Either these become the mechanism for real read-only narrowing (F1.4), or they should be deleted; today they are pure surface.

Resolved (#168). toolProfile became the read-only mechanism and gained a roster control; tools, disabledTools, and the phase-level copies were deleted, with normalize-on-read keeping older stored JSON loadable.

F3.6

Vocabulary leakage is partial

Phase kinds are already softened for operators (agent/command/checkpoint) — the right pattern. But "envelope" and "gate" leak verbatim everywhere.
▶

"Envelope kind — The typed reply this agent must return." "Create a pipeline to orchestrate bounded agent phases and command gates." These appear in the roster editor, phase editor, acceptance labels, inspector badges, and smith cards.

Resolved (#166). Operator-facing copy now says "report" and "check" across those surfaces. Type identifiers, IPC channels, store keys, and the model-facing prompts keep the original vocabulary.

F3.7

The per-run surface is already minimal

Request + pipeline + Start, with preflight rails. This is the model the rest of the app should converge toward.
▶

Starting a run needs three decisions and shows validation, missing-command detection, a readiness banner, and base-ref sync as rails. This is the cleanest surface in the product.

3Onboarding & in-app explanation

How much the app has to explain, and whether it could explain less by being simpler.

How it works today

Four steps: Welcome (unified concept diagram + landing guidance) → Providers → Ready → Project. Readiness remains a separate heavy flow.

F4.4

Readiness is the heaviest first-project step

11 criteria, a five-stage stepper, its own model picker — presented before the operator has seen a single run.
▶

The flow's copy is accurate and its states are well-labeled. The issue is sequencing and volume, not quality: readiness is a gate before the operator understands what a run is.

F4.5

Good copy worth keeping

The trust statements, the detection panel's rejected-vs-unrunnable distinction, the empty states that point at the next action.
▶

"Foundry never writes to your working tree — only to worktrees it creates." The detection panel distinguishes a command that's right but unrunnable from one that's simply wrong. Runs and PRs empty states each point at the next action. Keep these.

§What we won't do — and why

Ideas that looked promising but broke a fixed constraint or cost more than they saved.

✕
Turn repo-discovery back onIt violates the explicit rule that ancestor guide files must not change what a run does, and would make run behavior depend on uncontrolled repo files. The project card keeps control in the engine instead.
✕
A retrieval / embedding index of the repoAdds a dependency (forbidden here), a stale-index problem across worktrees, and the project card plus the agent's own tools cover the need at far lower complexity.
✕
One shared session for all agents in a runDestroys per-agent boundary attribution, rewind anchoring (which is per-phase per-session), and the roster-role-as-system-prompt model; compaction would also hit one giant context. The project card solves the same problem without touching sequencing.
✕
Drop the submit_envelope tool, rely on the output constraint aloneThe tool call is the primary structured channel today, and output-constraint support may vary by provider (assumption). The text-parse fallback exists because neither channel is universal. Removing redundancy (R3) doesn't require removing a channel.
✕
Auto-adopt updated builtin prompts on upgradeViolates "builtins are seeds; user-edited copies are never overwritten." The opt-in badge plus reset (R10) achieves the goal inside the constraint.
✕
Remove the .foundry-handoff folder as a quick winDeferred, not rejected: the planner's write boundary, the boundary carve-out, the executor's create/resume paths, and the template tokens all reference it. Ripping it out safely needs a real-worktree test pass. The quick win is only to stop advertising the tokens.
✕
Remove gates or acceptance kinds from the engineThey're cheap in code, invisible per-run, and the fail-closed design depends on them. The problem is UI exposure, not the mechanism.
✕
Paginate the read_phase_context chainConsidered for token control; the whole-chain dump is a deliberate escape hatch. Revisit only if traces show large chains pulled repeatedly (assumption).
✕
Move readiness entirely out of the productIts checks are the substrate for the project card and the marker-file contract affects run success odds. R15 resequences it instead.

§Glossary

The AI-facing words this report keeps. Foundry-specific ones are defined; the report also recommends renaming two of them.

run

One attempt to turn a request into reviewed code, in its own isolated worktree.

pipeline

The recipe of phases a run walks. "Plan → Build → Test → PR" is one.

phase

One step in a pipeline. An agent phase (AI), a command phase (shell), or a checkpoint (human).

agent

The AI that does one phase's work, with its own role, tools, and write boundary.

prompt

The instructions sent to the agent: a system role (identity + rules) and a user turn (the ask).

context

Everything the agent sees: its prompt, prior envelopes, tool results, and conversation so far.

envelope

The typed answer an agent must return. Validated against a schema. Report suggests renaming to "report" in the UI.

gate

A mechanical check on an agent's answer (e.g. "declared files exist"). Report suggests renaming to "check" in the UI.

worktree

An isolated copy of the repo the run works in. The operator's checkout is never touched.

session

A live agent conversation. Per-agent and run-long; one-shots open and close one per turn.

token

The unit a model reads and writes. Context cost = tokens; fewer = faster and cheaper.

compaction

Summarizing a session's history between phases when it nears the context limit.
