Foundry can be faster, and easier to understand.

This is an audit of how Foundry builds the prompts and context each agent phase receives, and how much of its configuration surface an operator actually needs. The prompt machinery is already disciplined — so the biggest wins are not "trim the prompts," but give agents what they're missing, delete what contradicts itself, and shrink the choices around it.

Every finding cites the file it came from. Two claims about model behavior are marked as assumptions — they couldn't be confirmed by reading code alone.

§The six biggest wins

Where the time and tokens are really going — and where the confusion really lives.

Highest impact

Agents rediscover the repo, every phase, every run

Discovery is off, and nothing replaces it. Each agent, in its own session, burns 5–15 tool calls re-reading README, manifests, and conventions before it can work. A once-per-project "project card" fixes it.

prompts.ts · pi/open-session.ts · builtin-agents.ts
Redundancy

The answer shape is sent three ways — then contradicted

The envelope schema reaches the model as a prompt example, a tool schema, and an output constraint. Meanwhile every correction message tells the model to reply as text, fighting the tool channel it was just told to use.

prompts.ts · envelopes.ts · gates.ts · boundary.ts
Quality

The sharpened brief dies after the plan phase

Refine exists to rewrite a rough request into a clean brief. Only plan ever sees it — build, review, and the PR writer all get the raw request back. One line in the pipeline fixes it.

builtin-pipelines.ts
Configuration

Settings has ~35 controls; ~6 matter

One setting is fully dead, one is renderer-only, one global key hides inside the project pane, three retry knobs interact with no model, and a section has zero controls. It can collapse to 3 panes and ~15 controls.

SettingsScreen.tsx · store/settings.ts
Dead surface

Pipeline/agent schema carries unusable knobs

Tool-profile fields exist with no UI and no consumer. A gate can be added in the UI that can only fail. The "reset to builtins" action is wired but unreachable. Every shipped pipeline ignores most of the knobs.

roster.ts · pipelines.ts · ipc/roster.ts
Onboarding

Three of six screens teach vocabulary the app could drop

"Envelope" and "gate" leak everywhere; three onboarding screens restate the same triad. Merge and landing — the things a new operator actually needs next — are undiscoverable until a run finishes.

1Prompts & context assembly

What each agent phase is told, and what it actually gets to see.

How it works today

Each phase renders an agent's system + user prompt templates, appends any declared-but-unreferenced inputs, then appends an answer-shape example. The system role is three layers: a Foundry harness replaces the model's default identity, the roster agent's role is added each turn, and repo-discovery is fully off — so no README or guide file ever enters context. Every phase gets all ten tools. Sessions are per-agent and run-long; compaction runs between phases at 80% full. Corrections are short deltas; a failed-test feedback loop re-sends the whole prompt.

F1.1

No repo conventions ever reach an agent

Discovery is off and nothing replaces it — every agent re-discovers the stack and conventions with tool calls, per phase, per run.
▶

Refiner is told "skim the repo first: README, top-level layout, manifests"; Finisher is told to match "the conventions already in this codebase." But with discovery off, each must burn tool calls to find them — per agent, per run, because builder / reviewer / finisher are separate sessions.

Foundry already runs read-only detection and readiness against the repo and stores the project's commands. The raw material for a repo summary already exists; it is just never assembled for run agents.

F1.2

No git context for the phases whose whole job is the diff

reviewer / finisher / pr_writer are told to "inspect the diff" but receive no changed-file list, no branch point, no diff stat.
▶

The {{branch}} and {{base_ref}} tokens exist in the prompt palette — and no builtin uses them, so the PR writer must discover the base ref itself with shell calls. The engine computes exactly this data after each phase (in the boundary check) and holds the branch-point SHA. It just never injects it.

F1.3

The answer shape ×3, the instruction ×3, and a contradiction

The envelope schema is present three ways per turn; the submit rule is stated three times; every correction tells the model to reply as text, not as a tool call.
▶

Per turn the shape rides as (a) the answer-example JSON in the prompt, (b) the submit_envelope tool schema, (c) the output constraint. The "call submit_envelope once…" line appears in the harness, the answer block, and the tool description.

Meanwhile every correction path instructs a text reply: "Reply again with ONLY this JSON object, no prose, no code fence." Both channels parse (structured first, text fallback), so it works — but the model is told two different things, and the full example JSON is regenerated into every envelope correction.

F1.4

"You are read-only" while holding write tools

Five agents are told not to touch files, yet they hold edit / write / bash. Enforcement is policy + post-hoc git revert — not the tool surface.
▶

Refiner, scout, reviewer, pr_writer, issue_writer all say "do not create, edit, or delete any file" while still having write tools registered. The read-only machinery already exists for one-shots (a read-only session simply has no write tool in its registry). A comment in the runner claims per-phase tool narrowing that does not exist in the wiring.

F1.5

The handoff-folder mechanism is vestigial

The engine makes the folder and lists it, but no shipped pipeline or prompt uses it. Envelopes actually flow through the trace, not this folder.
▶

The engine only creates the .foundry-handoff/ directory and lists its contents into a token. The real envelope handoff is written to the trace folder, not the worktree. Only the planner's write boundary even names the folder; no builtin pipeline declares handoff files as an input. Two template tokens, a boundary carve-out, and a directory per worktree exist to serve a path nothing shipped uses.

F1.6

The refined brief dies after the plan phase

In the ship/sdlc chains, refine's improved_request reaches only plan. Everything downstream gets the raw request again.
▶

The refiner's own contract says its output "must stand alone: whoever reads it never sees the draft" — but every downstream phase sees only the draft. The whole point of the refine phase is wasted on the phases that follow.

F1.7

The feedback loop re-sends the whole prompt

A red test jumps back to build and re-renders the entire phase prompt into the same session that already holds it.
▶

Envelope and gate corrections got this right — they're short deltas. The failed-test feedback loop did not: it re-renders request + declared envelopes + the answer block + the feedback section, and sends all of it again. On a large plan envelope this re-sends the biggest block in the run, once per feedback retry (default 2).

F1.8

One-shot prompt debris

A stale tool constant, a readiness rule stated three times, an instruction to "fan out sub-agents" when no sub-agent tool exists, and a first-run fill with less context than the settings flow.
▶

A DETECT_TOOLS constant is capitalized to match no real tool name and is unused. The readiness marker-ignore rule appears three times. The readiness system prompt tells the agent to "fan out. Use general sub-agents/workers…" — but no sub-agent tool is in the session's registry, so the instruction is unactionable.

The run-start command fill reuses the detect prompt but drops the manifest sniff that the interactive detect session includes — so the moment that matters most (first run) the agent works with strictly less context.

F1.9

SHELL_NOTE half-truths

"Credentials are already live" is appended even to read-only agents told not to run commands — and nothing tells the agent what setup actually ran.
▶

A fresh worktree has only run the setup script; toolchains are live only if setup installed them. The note asserts the operator's environment is live regardless, and is appended to agents told not to modify anything. Meanwhile the agent is never told whether setup succeeded.

F1.10

What's already good — keep it

The schema-driven example/constraint/parse triad; delta-only corrections; separate retry budgets; rewind-after-N; per-turn fresh envelope tool; trace-recorded prompts.
▶

One validation schema drives the answer example, the tool schema, the output constraint, and the parse — so they cannot drift. Corrections are short deltas into the live session. Envelope and gate retry budgets are separate. Rewind-after-N drops failed attempts from context. The envelope tool is rebuilt fresh per turn (validator-cache correctness). Every prompt is written to the trace for inspection. These are the right shape — don't churn them.

2Settings & config stores

How much of the settings surface an operator actually needs.

How it works today

Settings spans 6 panes — General / Providers / Agent defaults / Project / Maintenance / About — over 23 app settings plus per-project config (base ref, merge policy, commands, setup script, protected paths). Everything autosaves; credentials never live in settings. Validated-on-change with inline errors; atomic, self-healing config files.

F2.1

Dead and renderer-only settings

appearance has no control and no consumer anywhere. pollCadenceMs has a control but no main-process reader. project isolation has no UI at all.
▶

appearance (system/dark): fully dead — schema, default, type, and a mock are the only references. pollCadenceMs: a UI control ("Trace poll cadence") read only by the renderer, and the non-live cadence is already hardcoded there without a setting. Project isolation: consumed by the executor but settable in no UI — pipelines expose an isolation toggle, projects don't.

F2.2

Misplaced and half-merged

detectModel is a global key edited only inside the per-project pane. It already borrows the global reasoning effort — half-merged already.
▶

The detection model picker lives inside Settings → Project → Commands ("Who answers 'Ask AI'"), yet it's a global setting. Detection already reuses the global reasoning effort, so it's half-merged into defaults. The readiness model + effort are a second such pair sitting in Agent defaults.

F2.3

Three retry knobs, no stated interaction

Envelope retries, gate retries, and rewind-after-corrections interact — and an operator can't form a model of how from the UI.
▶

Three knobs (0–5, 0–5, 0–20). Every builtin pipeline phase already sets retries to 2, overriding the gate default anyway. The rewind knob's own schema comment says its useful range "stops well before a phase's retry budgets." The hints define mechanics using undefined terms ("Envelope retries — Correction messages sent when a reply will not parse").

F2.4

Sections that explain, not configure

"Autonomy" has zero controls. "Transport" exists for one port number whose hint admits the manager scans a band when busy. Duplicate doctor-checks and refresh-models buttons.
▶

The Autonomy section is pure prose. The Transport section exists to expose one number (the bridge port) — but the hint itself says the manager tries the next free port in the band when busy, so the preference adds almost nothing. Two panes render the same global doctor checks with different notes; "Refresh models" appears twice.

F2.5

Opaque copy

"Turn timeout" has no hint. "envelope", "vendored provider Bridge", "compact context", "corrections" are used in hints without definition.
▶

The Scope section is read-only and points to another screen ("Change scope in Design (⌘3)…"). Several hints define mechanics with vocabulary the operator has no way to learn in-place.

F2.6

The decision surface vs. the real surface

A fresh setup needs ~9–14 clicks and 5–8 decisions — but the operator faces ~35 controls to learn they can skip ~29 of them.
▶

The cost is not clicks; it is evaluation. An operator must read each control to know it doesn't matter. About six controls actually matter for setup: provider, repo, commands, setup script, readiness. The rest exist to be evaluated and dismissed.

F2.7

Good bones — keep them

Validated-on-change; atomic self-healing files; auto-save with no Save button; the "no credential is a setting" rule; the ⌘K settings palette.
▶

These are the right foundations. The redesign keeps all of them and only reshapes what's surfaced.

3Pipelines & agents

Whether the configuration model is more adjustable than it needs to be.

How it works today

9 built-in agents, 6 built-in pipelines, 6 gates, 9 envelope kinds, 4 acceptance kinds, 3 phase kinds. Operators can create / edit / duplicate / fork / delete agents and pipelines (builtins fork on rename, self-restore if deleted from the file, never overwritten by an upgrade). A run takes exactly three operator decisions: the request, the pipeline, and Start.

F3.1

Dead schema knobs

tools / disabledTools / toolProfile exist on both agents and phases with no UI, no engine consumer, and no builtin usage.
▶

There's even an empty {/* ── system tools ── */} placeholder in the roster editor waiting for a UI that never arrived. Either these become the mechanism for real read-only narrowing (F1.4), or they should be deleted; today they are pure surface.

F3.2

A UI trap: a gate you can add that can only fail

The editor lets you add the command_passes gate, but offers no field for its required command — so it always fails validation.
▶

A configuration path that can only produce an error. The gate needs a configured command; the editor only adds gates as bare names. There's no field to supply the argv.

F3.3

Knobs with exactly one value in practice

prompt.template is always 'user'. All 6 builtins use the same acceptance kind. timeoutMs, optional, per-phase model/envelope overrides, argv commands, checkpoint phases: zero shipped uses.
▶

Every built-in agent-phase retry count is 2; every feedback-retry count is 2. A great deal of the schema is there to express choices no shipped pipeline ever makes.

F3.4

Redundant restatement

Every built-in phase restates its agent's envelope, even though the engine already resolves "phase envelope, else agent envelope."
▶

The shipped data teaches editors the field is required when it's actually an override. An editor copying a built-in phase learns to fill a field that does nothing.

F3.5

Unreachable reset; unversioned builtins

"Reset to builtins" is wired over IPC but has no button. And edited builtins keep a stale prompt forever with no way to see or adopt the shipped update.
▶

Because builtins are seeds ("user-edited copies are never overwritten"), an operator who once tweaked builder keeps that tweak forever. A new shipped prompt only reaches fresh installs or an explicit reset — and the reset has no UI.

F3.6

Vocabulary leakage is partial

Phase kinds are already softened for operators (agent/command/checkpoint) — the right pattern. But "envelope" and "gate" leak verbatim everywhere.
▶

"Envelope kind — The typed reply this agent must return." "Create a pipeline to orchestrate bounded agent phases and command gates." These appear in the roster editor, phase editor, acceptance labels, inspector badges, and smith cards.

F3.7

The per-run surface is already minimal

Request + pipeline + Start, with preflight rails. This is the model the rest of the app should converge toward.
▶

Starting a run needs three decisions and shows validation, missing-command detection, a readiness banner, and base-ref sync as rails. This is the cleanest surface in the product.

4Onboarding & in-app explanation

How much the app has to explain, and whether it could explain less by being simpler.

How it works today

Six steps: Welcome → Factory → Roster → Providers (gated on a usable model) → Doctor (gated on blocking checks) → Project (gated on a selected repo). Three of six are purely conceptual. The first run then needs request + pipeline + Start; a new project also passes through command detection, setup generation, and the 11-criterion readiness flow.

F4.1

Three screens teach what one could

Welcome, Factory, and Roster all restate the same triad. The concepts an operator actually collides with first get zero onboarding mention.
▶

Roster's clarify line repeats Factory's lead nearly verbatim. Meanwhile command detection, the setup script, readiness, and merge — the things a new operator hits first — appear for the first time on the Runs empty state, never in onboarding.

F4.2

Jargon without definition at the moment of use

"Envelopes and gates decide success" before either is defined; "in-process on pi"; "bridge on {port}"; "signals" in doctor telemetry.
▶

"Usable model" is defined only tautologically (it "blocks setup"). Decorative SVGs show "gates 4/4" with no explanation. The vocabulary lands before the concept.

F4.3

Merge & landing is undiscoverable

Onboarding promises "merge on your terms" but where worktrees live and how work lands only appears after a run finishes.
▶

Nothing bridges "run accepted" to "so where is my code?" for a first-time operator. The merge / fix-with-agent / discard / create-PR actions live in the outcome banner of a finished run.

F4.4

Readiness is the heaviest first-project step

11 criteria, a five-stage stepper, its own model picker — presented before the operator has seen a single run.
▶

The flow's copy is accurate and its states are well-labeled. The issue is sequencing and volume, not quality: readiness is a gate before the operator understands what a run is.

F4.5

Good copy worth keeping

The trust statements, the detection panel's rejected-vs-unrunnable distinction, the empty states that point at the next action.
▶

"Foundry never writes to your working tree — only to worktrees it creates." The detection panel distinguishes a command that's right but unrunnable from one that's simply wrong. Runs and PRs empty states each point at the next action. Keep these.

§What we won't do — and why

Ideas that looked promising but broke a fixed constraint or cost more than they saved.

✕
Turn repo-discovery back onIt violates the explicit rule that ancestor guide files must not change what a run does, and would make run behavior depend on uncontrolled repo files. The project card keeps control in the engine instead.
✕
A retrieval / embedding index of the repoAdds a dependency (forbidden here), a stale-index problem across worktrees, and the project card plus the agent's own tools cover the need at far lower complexity.
✕
One shared session for all agents in a runDestroys per-agent boundary attribution, rewind anchoring (which is per-phase per-session), and the roster-role-as-system-prompt model; compaction would also hit one giant context. The project card solves the same problem without touching sequencing.
✕
Drop the submit_envelope tool, rely on the output constraint aloneThe tool call is the primary structured channel today, and output-constraint support may vary by provider (assumption). The text-parse fallback exists because neither channel is universal. Removing redundancy (R3) doesn't require removing a channel.
✕
Auto-adopt updated builtin prompts on upgradeViolates "builtins are seeds; user-edited copies are never overwritten." The opt-in badge plus reset (R10) achieves the goal inside the constraint.
✕
Remove the .foundry-handoff folder as a quick winDeferred, not rejected: the planner's write boundary, the boundary carve-out, the executor's create/resume paths, and the template tokens all reference it. Ripping it out safely needs a real-worktree test pass. The quick win is only to stop advertising the tokens.
✕
Remove gates or acceptance kinds from the engineThey're cheap in code, invisible per-run, and the fail-closed design depends on them. The problem is UI exposure, not the mechanism.
✕
Paginate the read_phase_context chainConsidered for token control; the whole-chain dump is a deliberate escape hatch. Revisit only if traces show large chains pulled repeatedly (assumption).
✕
Move readiness entirely out of the productIts checks are the substrate for the project card and the marker-file contract affects run success odds. R15 resequences it instead.

§Glossary

The AI-facing words this report keeps. Foundry-specific ones are defined; the report also recommends renaming two of them.

run

One attempt to turn a request into reviewed code, in its own isolated worktree.

pipeline

The recipe of phases a run walks. "Plan → Build → Test → PR" is one.

phase

One step in a pipeline. An agent phase (AI), a command phase (shell), or a checkpoint (human).

agent

The AI that does one phase's work, with its own role, tools, and write boundary.

prompt

The instructions sent to the agent: a system role (identity + rules) and a user turn (the ask).

context

Everything the agent sees: its prompt, prior envelopes, tool results, and conversation so far.

envelope

The typed answer an agent must return. Validated against a schema. Report suggests renaming to "report" in the UI.

gate

A mechanical check on an agent's answer (e.g. "declared files exist"). Report suggests renaming to "check" in the UI.

worktree

An isolated copy of the repo the run works in. The operator's checkout is never touched.

session

A live agent conversation. Per-agent and run-long; one-shots open and close one per turn.

token

The unit a model reads and writes. Context cost = tokens; fewer = faster and cheaper.

compaction

Summarizing a session's history between phases when it nears the context limit.
